# Architecture Decision Records

## ADR-001 — Ports on the production host
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The README suggests the engine server on 8080 and the Vite dev server on 5173. On the production host (c.referee.at) 8080 is used by an unrelated service and 5173 by another dev server.

**Decision.** The ChessLab server listens on `127.0.0.1:8580` by default (`PORT` env var). The Vite dev server uses `5180`. nginx terminates TLS and proxies `/ws` and `/health` to 8580.

**Consequences.** README dev section documents the new ports. Nothing is exposed directly; only nginx listens publicly.

## ADR-002 — Hosting model for c.referee.at
**Date:** 2026-10-23 · **Status:** accepted

**Context.** We need early, visible results and later server-mode analysis on the same machine. The host already runs nginx with certbot-managed vhosts.

**Decision.** Static frontend build is served by nginx from `/var/www/c.referee.at` with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (needed for multi-threaded WASM). TLS via Let's Encrypt (certbot nginx plugin). The engine server runs as a systemd service bound to localhost; nginx proxies `/ws`. Deployment config lives in `deploy/` in the repo. Docker compose (M6) remains for other hosts.

**Consequences.** All third-party resources must be same-origin or CORP-enabled (COEP). Deploy is a script, not CI (CI only tests).

## ADR-003 — Native Stockfish build target on this host
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The VM CPU (QEMU virtual CPU) exposes SSE4.1/SSE4.2/POPCNT but **no AVX2/BMI2**.

**Decision.** `scripts/fetch-engines.sh` must detect CPU flags and select the `x86-64-sse41-popcnt` Stockfish build when AVX2 is absent (AVX2/BMI2 builds otherwise). 16 cores / 30 GB RAM are available; engine pool limits will be sized accordingly in M3.

**Consequences.** Lower NPS than an AVX2 build; still far stronger than browser WASM.

## ADR-005 — Browser engine delivery (Stockfish WASM)
**Date:** 2026-10-23 · **Status:** accepted

**Context.** README §2.1 asks for the `stockfish` npm builds: `lite-single` by default and the multi-threaded build when COOP/COEP headers are present. `stockfish@19.0.1` ships classic, non-module Emscripten worker scripts that locate their `.wasm` by their own URL and spawn pthread workers from `self.location.href`; bundling or renaming them breaks that. Loading from a CDN is ruled out by COEP `require-corp` (ADR-002).

**Decision.** Depend on `stockfish@19.0.1` (pinned exactly). A Vite plugin (`apps/web/vite-plugin-stockfish.ts`) copies only `stockfish-19-lite{,-single}.{js,wasm}` unchanged to `assets/engine/stockfish-<version>/` and serves the same path in dev with COOP/COEP/CORP headers. The version in the directory name replaces content hashing, so the nginx `/assets/` rule (immutable cache, headers) covers the files unchanged. `WasmEngineClient` starts a classic `Worker`, uses `lite` with `min(cores-1, 4)` threads when `crossOriginIsolated`, otherwise `lite-single`. All scores leave the client from White's point of view (helpers in `engine-core/pov.ts`, shared with the future `RemoteEngineClient`). `analyze()` returns an `AnalysisHandle` (AsyncIterable plus `bestMove` promise) that still satisfies the `Engine` interface. The ~99 MB full builds are not shipped (deferred opt-in).

**Consequences.** All engine files are same-origin and work under COEP. Upgrading Stockfish bumps the pinned version, which changes the URL and busts the cache. `pnpm install` downloads the whole ~155 MB package in CI as well. Measured in headless Chromium on this VM: ~2.0 MNPS with 4 threads (`lite`), ~0.4 MNPS single-threaded.

## ADR-006 — Browser ⇄ server WebSocket protocol
**Date:** 2026-10-23 · **Status:** accepted

**Context.** Server mode (M3) streams native-engine analysis to the browser. The server (M3-2) and `RemoteEngineClient` (M3-4) are built by different agents and must agree on one contract up front. The browser side already consumes the `Engine`/`AnalysisHandle` shape through `UciSession` (one search per engine, a new `analyze` replaces the running one, scores converted to White's point of view in `engine-core/pov.ts`). M5 needs several engines per client in parallel. The server must protect a shared machine (16 cores, ADR-003) against expensive or malicious requests, and both sides use Zod v4 already (`apps/server`).

**Decision.** The protocol is defined once, as Zod schemas with inferred types, in `packages/engine-core/src/protocol.ts` (`zod` becomes a dependency of `engine-core`; no DOM/Node APIs). JSON text frames, one message per frame, discriminated by `type`.

- *Messages.* Client → server: `hello` (`protocolVersion`, optional `client {name, version}`), `analyze` (`sessionId`, `searchId`, `engine`, `fen`, optional `multipv`, `depth`, `movetime`, `threads`, `hash`), `stop {sessionId}`, `release {sessionId}`, `ping {t?}`. Server → client: `welcome` (`protocolVersion`, `serverVersion`, `limits`, `engines[] {id, name, enabled, defaults {threads, hash}}`), `info {sessionId, searchId, info: EngineInfo}`, `bestmove {sessionId, searchId, bestMove: BestMove | null, reason: completed | stopped | limit}`, `error {code, message, sessionId?, searchId?}`, `pong {t?}`. There is no `setOptions` message: the only client-settable UCI options are `Threads` and `Hash`, carried on every `analyze` (typed fields, so arbitrary UCI options such as `Debug Log File` or `EvalFile` cannot reach a native process), which also makes `analyze` self-contained and sessions recreatable.
- *Session model.* `sessionId` is **client-chosen** (`[A-Za-z0-9_-]{1,64}`, scoped to the connection) so that `RemoteEngineClient.analyze()` can return an `AnalysisHandle` synchronously and `stop` needs no round trip. A session leases one engine instance; it is created implicitly by the first `analyze`, freed by `release`, by a server idle timeout (no running search) or when the socket closes (all sessions of the connection are stopped and released; nothing survives a reconnect). `searchId` (client-chosen positive integer, unique per session; a counter) identifies one `go`; it is echoed on `info`, `bestmove` and search-level `error` so the client can attribute every message even when it has already queued the next search. A new `analyze` on a session with a running search stops it (`bestmove … reason: stopped` is delivered before any `info` of the new search), mirroring `UciSession`. Every accepted search ends with exactly one terminal message: `bestmove`, or an `error` carrying its `searchId`. `error` with `sessionId` only is session-level (`engine_crashed` releases the session); `error` without `sessionId` is connection-level. `stop` on an idle session is a no-op; `release` is idempotent.
- *Point of view.* The server relays **raw UCI, side-to-move scores**; it does not convert. The client already knows the FEN of each search and applies `infoToWhitePov(info, sideToMove(fen))`, exactly as `UciSession` does for WASM, so there is a single, tested conversion path and the server stays a transparent UCI relay (`info.info` is exactly `EngineInfo`, enforced by a compile-time assignability check).
- *Handshake and versioning.* The first client message must be `hello`; the server answers `welcome` or `error: protocol_mismatch` and closes (WebSocket close code 1008). Any other message before `hello` → `handshake_required`. `PROTOCOL_VERSION = 1` is bumped on incompatible changes; additive optional fields do not require a bump because unknown fields are **stripped**, not rejected (unknown `type` is rejected).
- *Limits.* Two layers: hard ceilings baked into the schemas (`PROTOCOL_BOUNDS`: depth 1–99, movetime 100–600 000 ms, multipv 1–10, threads 1–64, hash 1–16 384 MB, FEN ≤ 100 chars, pv ≤ 300 moves, frame ≤ 16 KiB → `invalid_message`), and per-connection `Limits` the server announces in `welcome.limits` (`DEFAULT_LIMITS`: depth 30, multipv 5, threads 4, hash 512 MB, movetime 600 s, 2 sessions per connection; overridable by `MAX_*` env vars) checked with the shared `checkAnalyzeLimits()` → `limit_exceeded`. Global capacity (`MAX_SESSIONS`, `maxInstances` per engine) is server-side → `no_capacity`. FENs are validated syntactically (`isValidFen`: 8 ranks of 8 squares, exactly one king per side, side, castling incl. Chess960 letters, en passant, optional counters) before they reach a native process; newlines can therefore not be injected into UCI commands.
- *Error codes.* `invalid_message`, `protocol_mismatch`, `handshake_required`, `unknown_engine`, `limit_exceeded`, `no_capacity`, `session_not_found`, `engine_crashed`, `rate_limited`, `internal_error`.
- *Parsing.* `parseClientMessage()`/`parseServerMessage()` accept JSON text or a parsed value and return `{ ok: true, message } | { ok: false, error }` with `type: path: message` diagnostics; both sides validate outgoing as well as incoming messages in tests.

**Consequences.** M3-2 and M3-4 can be implemented independently against `@chesslab/engine-core`; the server sets `ws` `maxPayload` to `MAX_MESSAGE_BYTES`, maps `analyze.threads/hash` to `setoption`, and must emit the previous search's `bestmove` before the next search's `info`. `RemoteEngineClient` keeps a map `(sessionId, searchId) → handle`, converts POV itself and can fail fast using `welcome.limits`. `zod` ships to the browser bundle (≈ 15 kB gzipped). Changing message shapes incompatibly means bumping `PROTOCOL_VERSION` and this ADR. Engine-specific UCI options (Elo, skill level, variants) are deliberately not exposed; adding them later is an additive change (`analyze.options` with a server-side allow-list).


## ADR-007 — Engine server policies (apps/server)
**Date:** 2026-10-23 · **Status:** accepted

**Context.** ADR-006 fixes the wire protocol; the server (M3-2) still had to decide resource and abuse policies for a shared 16-core host.

**Decision.**
- Every search has a wall-clock cap: `MAX_MOVETIME_MS` (600 s default), or `movetime + 2 s`. Hitting it ends the search with `bestmove … reason: 'limit'`.
- Sessions without a running search give their engine back after `SESSION_IDLE_MS` (10 min) and are recreated transparently on the next `analyze`. Idle engine processes beyond one per engine are killed after `ENGINE_IDLE_MS` (5 min).
- Backpressure: `info` messages are dropped while a socket buffers more than 1 MiB; terminal (`bestmove`) and `error` messages are never dropped.
- Rate limits: more than 20 `analyze`/s per connection → `rate_limited`; more than 100 messages/s of any type → `rate_limited` and close 1008. Handshake timeout 10 s → close 1008. Heartbeat ping every 30 s.
- `invalid_message` for a malformed `analyze` carries `sessionId`/`searchId` when they parse, so clients can settle the handle.
- Only `Threads`, `Hash`, `MultiPV` (and `UCI_Chess960`, currently unused) can ever reach a native process; option values are cached so an unchanged `Hash` is not re-sent.
- All outgoing messages are validated against `ServerMessageSchema` (always on; invalid ones are logged and dropped).
- Enabled engines whose binary is missing are listed as disabled.

**Consequences.** Defaults (`MAX_SESSIONS=4`, `MAX_THREADS=4`, `maxInstances=3`) use at most 12 of 16 cores. Per-IP limit: nginx `limit_conn chesslab_ws 10` on `/ws` (429 above). Open: no Origin check yet (M6-3 security review).

## ADR-008 — Security policies for the public engine server (M6-3)
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The engine server is a public, unauthenticated WebSocket in front of native processes (ADR-006/007). The M6-3 review (`docs/SECURITY.md`) found three things that needed a policy rather than a patch: browsers attach the page's `Origin` to every WebSocket handshake and apply no CORS to it, so any website could open `/ws` from a visitor's browser (cross-site WebSocket hijacking) and spend that visitor's per-IP quota; Stockfish 19 strictly validates `position fen` and terminates the process (`exit(1)`, no `bestmove`) on positions that pass the syntactic `isValidFen` — adjacent kings, a king capturable by the side to move, pawns on the first/eighth rank, more than 8 pawns or more promoted pieces than missing pawns, more than 32 pieces, an en-passant square on the wrong rank — which made every such `analyze` a cheap engine respawn (~100 MB binary + NNUE init); and `scripts/fetch-engines.sh` verified the Stockfish download only when `jq` happened to be installed (it is not, on the production host).

**Decision.**
- *Origin policy* (`apps/server/src/ws/origin.ts`, env `ALLOWED_ORIGINS`). Enforced at upgrade time, before `ws` sees the socket; a rejected handshake gets HTTP 403 and a `warn` log line. Requests without an `Origin` header are accepted (only browsers send it; a non-browser client can forge any value, so rejecting its absence would break tooling without adding security). `ALLOWED_ORIGINS` is a comma-separated list of `scheme://host[:port]` origins (normalised, exact match) or `*` (check disabled); a malformed entry fails startup. Unset, the origin's host name must equal the request's `Host` name (ports ignored because the proxy forwards `Host` without one), or both must be loopback (Vite on :5180 → server on :8580). Production sets `ALLOWED_ORIGINS=https://c.referee.at` in the unit; Docker compose relies on the same-host default so any `WEB_PORT` works.
- *FEN validation mirrors Stockfish.* `isValidFen` (engine-core, shared by both sides) now rejects exactly what `Position::set` rejects, so a client-supplied position can never terminate an engine; it still accepts what Stockfish merely sanitises (bogus castling rights, an en-passant square without a capturable pawn). This is stricter input validation, not a wire change: `PROTOCOL_VERSION` stays 1.
- *Verified engine downloads.* `fetch-engines.sh` fails closed: the asset's sha256 must match the digest GitHub publishes for the release (parsed with `jq` or `node`) and, when set, `STOCKFISH_SHA256`; downloads only from `github.com`/`objects.githubusercontent.com`; `--no-verify` downgrades a missing digest/tool to a warning. The Docker image pins `STOCKFISH_VERSION=sf_19` and its digest.
- *Health split.* Public `/health` returns `{status, version}`; pool statistics (busy/idle engines, sessions, connections) moved to `/health/detail`, which nginx does not proxy.
- *Host hardening* applied live: systemd `CapabilityBoundingSet=`, `SystemCallFilter=@system-service` (+`SystemCallErrorNumber=EPERM`, `SystemCallArchitectures=native`), `IPAddressDeny=any`/`IPAddressAllow=localhost` (no egress), `ProtectProc=invisible`, `ProtectClock/Hostname/KernelLogs`, `RestrictNamespaces/Realtime`, `RemoveIPC`, `UMask=0077`; nginx `limit_req` 5 handshakes/s (burst 20) per IP on `/ws` next to the existing `limit_conn 10`, and `Content-Security-Policy: frame-ancestors 'none'`; Docker `server` runs read-only with `cap_drop: ALL` and `no-new-privileges`.

**Consequences.** Hosting the web app on a different origin than the server now requires `ALLOWED_ORIGINS`. `deploy/nginx/c.referee.at.conf` (committed empty by mistake in 47cffbf) is restored and is again the source for the live vhost. `ProcSubset=pid` is deliberately not set (Stockfish and libuv read `/proc/cpuinfo`, `/proc/stat`). Residual risks and the prioritised backlog (per-IP session cap, full CSP, base-image digests, respawn backoff) are in `docs/SECURITY.md`.

**Addendum (2026-10-23): per-IP session cap and respawn backoff** (the two P1 items of `docs/SECURITY.md` §4).
- *Per-IP session cap.* `MAX_SESSIONS_PER_IP` (default `min(2, MAX_SESSIONS)`; larger than `MAX_SESSIONS` fails startup) limits engine sessions that hold or are acquiring a lease, per client address and across all of its connections; one `IpSessionLedger` per WebSocket server. Reserved synchronously right before `pool.acquire` and released wherever the lease is dropped, so idle sessions without a lease do not count. Refusal reuses `no_capacity` (message "too many sessions from your address") — no protocol change, `PROTOCOL_VERSION` stays 1. Client address: `X-Real-IP` only if the TCP peer is loopback or listed in `TRUSTED_PROXIES` (`*` = any peer, used by Docker compose where nginx is another container and 8580 is not published), else the peer address; normalised (IPv4-mapped IPv6 unwrapped, zones stripped).
- *Respawn backoff.* Per engine, the pool counts consecutive crashes (unexpected exits, failed starts; exits the pool caused are not crashes). After the n-th it refuses to spawn that engine for `min(500 ms · 2^(n−1), 30 s)` with ±20 % jitter; such `acquire`s return `no_capacity` immediately instead of waiting (idle instances are still leased). Reset when an instance stays up `ENGINE_CRASH_RESET_MS` (60 s) or a search on it ends with `bestmove` (`pool.reportHealthy`); a running backoff is not shortened. From `ENGINE_MAX_CONSECUTIVE_CRASHES` (10) on, the engine is `degraded` and the delay stays at 30 s. Visible only in `/health/detail` (`crashes`, `backoffUntil`, `degraded`); `welcome.engines[].enabled` keeps the configured value.
- *Consequence.* A client whose search crashed an engine sees `no_capacity` for ~0.5 s if it retries at once (the web client shows "Server busy, try again"). `/health/detail` gains `clientAddresses`.

## ADR-009 — Multi-engine analysis store
**Date:** 2026-10-23 · **Status:** accepted (shared settings superseded by ADR-010)

**Context.** M5-1 lets users run several engines (browser WASM builds, server engines) on the same position side by side. The single-engine store (`settings.backend`) could not express that.

**Decision.** Engines are identified by registry keys (`wasm:lite`, `wasm:lite-single`, `remote:<engineId>`; `apps/web/src/engine/registry.ts`). The analysis store keeps shared `fen`/`terminal`/`settings` (depth, MultiPV, threads apply to all engines) and per-engine state in `instances[key]`, with one `AnalysisController` per enabled key. `enabledEngines` is persisted; a master `enabled` switch stops/resumes all. Server engines are discovered by a probe (`hello`/`welcome`, cached 60 s). Resource guard: at most one of each WASM build and two server engines. `selectPrimary` (first enabled engine) feeds the eval bar and the best-move arrow. Old persisted settings (`backend: 'remote'`) migrate to `['remote:stockfish']`.

**Consequences.** Settings are shared across engines (per-engine settings would be a product decision). The probe opens a short extra WebSocket connection when the picker opens. The engine factory signature in `startAnalysisController` is `(spec, settings)`.

## ADR-010 — Per-engine settings, server access token, full-strength browser build
**Date:** 2026-10-23 · **Status:** accepted

**Context.** Product decisions after M5/M6 (PLAN M9-1..M9-4): engines compared side by side need their own depth/MultiPV/threads (a fast browser engine and a deep server engine rarely want the same limits); the public engine server should be closable to a known group without accounts; users with fast machines want the full-strength Stockfish network in the browser; the AnalysisPanel unit tests depended on the CI machine's core count.

**Decision.**
- *Per-engine settings* (`apps/web/src/store/analysisStore.ts`). `settings` stays the global default (plus the global `remoteUrl`). New `engineSettings: Record<EngineKey, Partial<{depth, multipv, threads}>>` holds overrides per registry key, persisted in `chesslab.analysis` (also for engines that are currently disabled; omitted when empty, so the old shape still loads and is still written when nobody overrides anything). Each controller runs with `effectiveSettings(state, key)` = defaults merged with the override; MultiPV line merging uses the engine's own value. Actions: `setEngineSettings(key, patch)` (`null` removes a field), `applySettingsToAll(key)` (the engine's effective settings become the defaults, all overrides are cleared). UI: with two or more engines the Depth/Lines/Threads selects edit the selected tab's engine, labelled "Settings for <engine>", with an "Apply to all" link; with one engine they edit the defaults (and drop that engine's override of the changed field), so the single-engine panel is unchanged.
- *Server access token* (protocol, additive). `hello` gains optional `token` (string, ≤ 256 = `MAX_TOKEN_LENGTH`); new error code `unauthorized`. `PROTOCOL_VERSION` stays 1: old clients against a public server and new clients against an old server both keep working (an old server ignores the unknown field). Server env `ACCESS_TOKEN` (optional; empty = public). If set, `hello.token` is compared in constant time (SHA-256 of both sides + `timingSafeEqual`); missing/wrong → `error unauthorized` and close 1008, before `welcome` (so no engine list or limits leak). The token is never logged (only `tokenSent: true|false`). It travels only in `hello`, not in the URL or `Sec-WebSocket-Protocol`, so it does not appear in nginx access logs. Web: Settings tab "Server access token" (password input with show/hide, explicit Save), stored as `serverToken` in `chesslab.settings`; `RemoteEngineClient({ token })`; the store's probe and engine factories pass it; saving a new token drops the probe cache and reconnects all server engines. `unauthorized` is shown as "Access token required or wrong" with a pointer to the Settings tab (engine status, panel, picker). `deploy/ws-smoke.mjs` and `deploy/ws-limits-check.mjs` read `CHESSLAB_TOKEN`.
- *Full-strength WASM build* (opt-in). `vite-plugin-stockfish.ts` also ships `stockfish-19.js` + `stockfish-19.wasm` (multi-threaded, full NNUE embedded, 99,076,105 bytes, ~79 MB gzip) next to the lite builds; `__STOCKFISH_ENGINE__.sizes` carries download sizes. `WasmBuild = 'lite' | 'lite-single' | 'full'`; registry key `wasm:full`, labelled "Stockfish 19 (browser, maximum strength, ~99 MB download)", badge "browser max", available only on cross-origin isolated pages, `capabilities().build = stockfish-19.0.1-full`. `wasm:lite` and `wasm:full` are mutually exclusive (`displacedBy`): enabling one replaces the other in its tab position with a hint, so there is still at most one multi-threaded WASM engine. Before the first download the picker asks for confirmation (remembered in `localStorage` `chesslab.fullBuildConfirmed`). The file is fetched only when the engine is enabled; it is versioned under `assets/engine/stockfish-<version>/` like the others.
- *Deterministic UI tests.* The page capabilities (`crossOriginIsolated`, `hardwareConcurrency`) live in the analysis store as `env` (initialised from `currentEnv()`); the panel and picker read them from there instead of `navigator`, and tests set them explicitly. Picker labels are unique on every machine: "browser, multi-thread, N threads" / "browser, single-thread" / "browser, maximum strength, ~N MB download".

**Consequences.** Enabling the token on production locks out the deployed web build until users enter the token (old builds send none). The token is a shared secret in each user's `localStorage` — a gate against casual/anonymous use, not per-user authentication; rotating it means editing `.env.production`, restarting the service and handing out the new value. `dist/` grows by ~99 MB (rsync deploys transfer it once per Stockfish version). Server engines without overrides follow later changes of the defaults; an override survives disabling and re-enabling its engine.

## ADR-011 — Automatic review, opening data and the lichess explorer
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The product owner asked for automatic analysis of loaded games with concrete suggestions, opening identification, and statistics on whether/how often a position was played, by whom and with which result.

**Decision.**
- *Auto review.* Loading a game (PGN paste/file, lichess/chess.com import, explorer) starts a review with the Fast preset (setting `autoReview`, default on; never while a game against the engine is running). The side panel switches to the Review tab except when the load came from the Explorer tab. Per-move details (played vs. best move, best line, evals, swing) are built in the web layer (`review/details.ts`); `engine-core`'s `ReviewSummary` is unchanged.
- *Openings.* ECO code and name come from a vendored, CC0 lichess `chess-openings` table (`apps/web/src/openings/data/openings.json`, generated by `apps/web/scripts/build-openings.mjs`, lazy chunk ~63 kB gzip), matched by position (EPD) so transpositions are recognised. No API call.
- *Explorer.* Position statistics use the lichess Opening Explorer at `https://explorer.lichess.org` (masters and lichess databases). Since November 2025 lichess requires an OAuth token for every explorer request (announced in the lichess blog); the app therefore asks the user for a free, scopeless lichess API token, stored only in localStorage (`chesslab.explorer`) and sent only as an `Authorization` header. `connect-src` in the CSP includes `https://explorer.lichess.org`. Requests are debounced (300 ms), cached (LRU 200) and stopped beyond 50 plies; 429 is honoured via `Retry-After`.

**Consequences.** Without a lichess token the Explorer tab shows an explanatory message; everything else works offline. The explorer's rate limit (~20 requests/min per user) bounds how fast one can browse positions. "Log in with lichess" (OAuth PKCE) would remove the token paste and is a possible follow-up.

## ADR-012 — lichess login and live games
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The product owner wants to play live on lichess inside ChessLab and to use their lichess account for the explorer and game import.

**Decision.**
- *Login.* OAuth 2.0 PKCE against lichess (`client_id` `chesslab.c.referee.at`, redirect to the app's own origin, scopes `board:play challenge:read challenge:write`). The token lives in localStorage `chesslab.lichess`, is sent only as an `Authorization` header to `lichess.org`/`explorer.lichess.org`, is revoked on logout, and never appears in URLs, logs or error strings. Shared interface: `apps/web/src/lichess/auth.ts` (`useLichessAuth`, `getLichessToken`, `lichessFetch`, `hasScope`).
- *Live games.* lichess Board API (event stream, game stream, seek/challenge/AI, move/resign/abort/draw/claim-victory) via NDJSON streams with reconnect; lichess is the source of truth and is mirrored into the game store. Lobby seeks are limited to Rapid/Classical by lichess; Blitz works for direct challenges and the AI.
- *Fair play.* A single lock (`apps/web/src/live/lock.ts`) disables live analysis, review and the engine while a live game (or a local engine game) runs; it is not bypassable from the UI. A local engine game and a live game are mutually exclusive. The auto review starts only after the live game has finished.
- *Premoves.* `settings.premoves` = `none | single | queue` (default `single`); `queue` is managed by the app (ordered, cleared on illegality or Escape) and applies to live and local engine games.

**Consequences.** Users must log in on lichess once per browser; a manual login on the production origin should be confirmed. Chat, takebacks and rematch via the Board API are not implemented. The explorer and import also use the login token, removing the token paste for logged-in users.

## ADR-013 — Play a friend via link: rooms on the engine server
**Date:** 2026-10-23 · **Status:** accepted

**Context.** The product owner wants to "offer online games via a link: just generate a link and pick a nickname before the game" (PLAN M16). No accounts, no lichess. The server already has a WebSocket endpoint with handshake, Origin check, per-IP accounting and rate limits (ADR-006/007/008), so a second transport would be waste; but it is also token-protected in production (ADR-010), and friends following a link will not have the token. The web client has clock semantics (`apps/web/src/clock/gameClock.ts`: Fischer increment, monotonic charging) and a live-game shape (`LiveGameController`: a mirrored, server-authoritative game with `wtime/btime/lastStateAt`) that the new mode should reuse rather than reinvent. The server must stay cheap: games are short, rooms are few, and the host is shared with the engine pool.

**Decision.**

- *Transport and shape.* Rooms are additive `room.*` messages on the existing `/ws` protocol (`packages/engine-core/src/protocol.ts`), `PROTOCOL_VERSION` stays 1: every new message has a new `type` (old servers reject it as `invalid_message`, old clients never send it), `welcome.capabilities` is optional, `forbidden` is an added error code, and no existing field changed shape. The server is the **authority** for rules and clocks (chess.js on the server, same major as the web). After every change it sends the **full snapshot** `room.state` to every member of the room; nothing is sent incrementally, so the client can always replace its state (the same "mirror" approach as the lichess live game). Room-level failures come as `room.error {roomId?, code, message}` so that `RemoteEngineClient`, which handles `error`, is never confused by them; envelope failures (`invalid_message`, `rate_limited`, `handshake_required`) stay on `error`.
- *Message catalogue (client → server).* All but `room.create` carry `roomId`; a connection is a member of **one room at a time** (creating/joining/attaching another leaves the current one; a player seat left this way is marked disconnected, not freed).
  - `room.create {nick, clock: {initialMs, incrementMs} | null, color: white|black|random}` — host; answer `room.seat` + `room.state`.
  - `room.join {roomId, nick?}` — with `nick` takes the free seat (the game starts) or, if both seats are taken, spectates; without `nick` only spectates. Player: `room.seat` + `room.state`; spectator: `room.state` (`you: 'spectator'`).
  - `room.attach {roomId, playerToken}` — re-takes a seat (reload, new tab, reconnect); a connection still holding that seat is demoted to spectator (gets a `room.state` with `you: 'spectator'`). Answer `room.state`. Attaching to the seat one already holds just resends the state.
  - `room.move {roomId, uci}` (promotion as 5th char), `room.resign`, `room.draw {action: offer|accept|decline}`, `room.abort`, `room.claim`, `room.leave` (spectator removed; player marked disconnected, same as a socket close).
- *Message catalogue (server → client).*
  - `room.seat {roomId, playerToken, color}` — whenever the connection takes a seat (create, join with a free seat).
  - `room.state {roomId, status: waiting|playing|finished, players: {white?: {nick, connected}, black?: {…}}, you: white|black|spectator, spectators, startFen, fen, moves: uci[], clock: {initialMs, incrementMs, white, black, running: side|null} | null, drawOffer?: side, claimableAt?: epochMs, result?: 1-0|0-1|1/2-1/2, reason?: checkmate|stalemate|draw|resign|timeout|abort|abandoned|agreement, serverTime: epochMs}`. `fen` is a convenience (the client may replay `moves`); SANs are not sent (the client has chess.js; a 1000-ply snapshot must stay under the 16 KiB frame). A finished room without `result` was aborted/abandoned before a game was played.
  - `room.error {roomId?, code, message}` with codes `room_not_found`, `room_full`, `bad_token`, `not_a_player`, `not_your_turn`, `illegal_move`, `bad_state` (action not allowed now: abort after move 2, accept without offer, claim too early …), `too_many_rooms`.
  - `welcome.capabilities {analysis, rooms}` (optional, see access token below).
- *Rules.* Standard start position only. chess.js validates every move and detects checkmate, stalemate and the automatic draws (threefold, 50 moves, insufficient material → `reason: draw`); at 1000 plies (`ROOM_BOUNDS.maxPlies`) the game is adjudicated a draw (keeps snapshots bounded; practically unreachable). A move clears a pending draw offer; offering while the opponent's offer is pending accepts it; `decline` withdraws or declines. `abort` works in a waiting room (host cancels the link) and in a game before both sides have moved; afterwards only `resign`.
- *Clocks* (`apps/server/src/rooms/room.ts`, same semantics as the web's `gameClock` and lichess): Fischer increment; the **first two plies are untimed** and get no increment; from the third ply the side to move is charged on move arrival with the server's monotonic clock, receives the increment, and the opponent's clock starts. The server arms a timer for the running side's deadline; firing it flags → `reason: timeout`, the opponent wins unless they have no mating material (bare king, king + knight, king + same-coloured bishops → draw). A move arriving after the flag is rejected (`bad_state`) and the timeout snapshot is published first. `clock: null` = nothing ticks. `room.state.clock.white/black` are "as of `serverTime`"; the client displays `clock[running] - (now - receivedAt)` with its **own** arrival time (skew-free, like `LiveGame.lastStateAt`), and uses `serverTime` only to order snapshots and for the `claimableAt` countdown.
- *Disconnects and claims.* Closing the socket (or `room.leave`) marks the player `connected: false`; the clock keeps running. The opponent's snapshot carries `claimableAt` (= disconnect + `ROOM_CLAIM_GRACE_MS`, default 60 s); when it passes the server pushes another snapshot, and `room.claim` ends the game: a win (`reason: abandoned`) if both sides had moved, otherwise an abort without result. Both players gone for the grace period → `abandoned` by the server. A player comes back with `room.attach {roomId, playerToken}`: the token (256 random bits, base64url, 43 chars) is returned once in `room.seat`, compared in constant time (shared `tokenMatches`), never logged, never in the URL. Room ids are 128 random bits (22 chars, URL-safe).
- *Spectators.* Anyone with the link after both seats are taken (or joining without a nick) gets read-only snapshots; capped per room (`ROOM_MAX_SPECTATORS`, 10). Free with the snapshot model.
- *Lifecycle and limits* (`apps/server/src/rooms/RoomManager.ts`, env `ROOM_*`, defaults): `ROOM_MAX_ROOMS` 200 live rooms; `ROOM_CREATE_PER_IP` 10 per `ROOM_CREATE_WINDOW_MS` 10 min (client address from the existing `resolveClientIp`); a waiting room is abandoned after `ROOM_WAITING_TTL_MS` 15 min (host gets a final `finished/abandoned` snapshot, room deleted at once); a running game without a move for `ROOM_IDLE_TTL_MS` 2 h is abandoned; finished rooms are kept `ROOM_FINISHED_TTL_MS` 10 min (a reload after the game still shows the result) then deleted; `room.*` messages are limited to 10/s per connection (`rate_limited` on `error`, on top of the existing 100 msg/s). Nicks: 1–20 characters after `normalizeNick` (controls, bidi/format characters stripped, whitespace collapsed, trimmed; the schema applies it, so the server never stores anything else). Everything is in memory; rooms do not survive a restart (acceptable: games are short, and the client tells the user `room_not_found`).
- *Access token (changes ADR-010).* With `ACCESS_TOKEN` set, a `hello` whose token is missing or wrong is **no longer rejected**: the connection gets a restricted `welcome` — `engines: []`, `capabilities: {analysis: false, rooms: true}`, limits as usual — and every `analyze` is answered with `error unauthorized` (carrying its ids) while the socket stays open and `room.*` works. A correct token gives `capabilities: {analysis: true, rooms: true}` and the engine list as before; the constant-time check is unchanged. The client knows whether it sent a token, so `analysis: false` means "token required or wrong" to it. Old servers omit `capabilities` (= `{analysis: true, rooms: false}`). Logged at `info` with `tokenSent` only.
- *Fair play.* While a connection is a **player** in a `playing` room, `analyze` is rejected with `forbidden`; its engine sessions are dropped (`bestmove … stopped`) when the game starts. Spectators may analyse. The web client additionally locks its own engines (ADR-012 lock) — the server rule only closes the obvious loophole of analysing on the server with the same socket.
- *Logging.* Room id, colour, nick and connection id at `info` for create/join/attach/leave/expiry; tokens never. Abuse paths (`too_many_rooms`, wrong token) log like the existing limit refusals.
- *Infrastructure.* Nothing changes for nginx (`/ws` is already proxied; the 10 connections / 5 handshakes per second per IP still apply — two players and a few spectators at one address fit). `/health/detail` gains `rooms {rooms, waiting, playing, finished, members}`. No new variable is required in `.env.production` or the unit; the `ROOM_*` defaults are production-ready.

**Client guidance for M16-2 (web).**
- *Link.* `https://c.referee.at/#/room/<roomId>` (hash route: there is no router and the SPA shell is served for `/` only; the hash never reaches nginx logs or the server). The app parses `location.hash` on load; the room id is also acceptable as `?room=` if a router is ever added, but the hash is the committed form.
- *Flow.* Host: Play tab → "Friend" → nick, time control (`LOCAL_TIME_CONTROLS` presets, custom, or no clock → `clock: null`), colour → `room.create` → show the link + "waiting" until `status: playing`. Guest: open the link → the app connects to `/ws` (no token needed) → nick prompt → `room.join {roomId, nick}` → `room.seat` means playing, `room.state` with `you: 'spectator'` means watching. Store `playerToken` per room in `localStorage` (`chesslab.room.<roomId>` = `{playerToken, color, nick}`); on load with a hash and a stored token, send `room.attach` first, fall back to `room.join` on `bad_token`/absence, and show `room_not_found` as "This game link has expired".
- *State.* Treat `room.state` like `LiveGame`: replace the store from `moves` (replay with chess.js as `replay()` does), `you` is the orientation, `players[you].connected`, `clock`, `drawOffer`, `claimableAt`, `result/reason`. Keep `receivedAt = Date.now()` per snapshot; remaining time of `clock.running` = `clock[running] - (Date.now() - receivedAt)`, the other side is static; before `moves.length >= 2` nothing ticks. Flagging is the server's decision — show 0:00 and wait for the `timeout` snapshot. "Claim victory" button when `claimableAt` is set and `Date.now() + (serverTime - receivedAt-skew) >= claimableAt`; the server pushes a snapshot at that moment anyway, so enabling it on `serverTime >= claimableAt` of the latest snapshot is enough.
- *Fair play.* Lock engines/review (`lock.ts`) from `status: playing` until `finished`, exactly as for lichess games; then offer the automatic review.
- *Errors.* `room.error` is per request: show `message` inline (toast); `illegal_move`/`not_your_turn` roll back the optimistic move; `bad_state` for abort/claim/draw are informational. `error rate_limited` and `invalid_message` are bugs on the client side.
- *Restricted welcome.* `capabilities.analysis === false` must be mapped to `UNAUTHORIZED_MESSAGE` in `RemoteEngineClient`/the probe (today a `welcome` with no engines reads "Engine server has no enabled engine"); the rooms feature itself needs no token.

**Consequences.** The deployed web build sees a behaviour change on the token-protected server before M16-2 ships: without a token it now receives a restricted `welcome` (empty engine list) instead of `unauthorized` + close, which the current UI shows as "no enabled engine" rather than "token required" — deploy server and web together or accept the wording for the interim. `chess.js` becomes a server dependency (BSD-2). Rooms are per process and in memory: a restart ends all games; `MAX_ROOMS=200` with ≤ 12 members each bounds memory to well under 50 MB. `deploy/ws-smoke.mjs` treats `capabilities.analysis: false` as the token failure. ADR-010's sentence "missing/wrong → `error unauthorized` and close 1008, before `welcome`" is superseded by the restricted mode above.

## ADR-014 — Game review on the server
**Date:** 2026-10-25 · **Status:** accepted (M17-1)

**Context.** The game review (ADR-011, `apps/web/src/review/`) always ran on the browser WASM engine; on an iPad or an older laptop a Deep review takes minutes. The production engine server (16 vCPU, native Stockfish 19, `ACCESS_TOKEN`) is far faster and already serves the live analysis through `RemoteEngineClient` (ADR-006 protocol). `BatchAnalyzer` needs the `Engine` interface of `packages/engine-core`, which `RemoteEngineClient` already satisfies structurally (White-POV scores, `bestMove` on the handle). The server caps sessions per address (`MAX_SESSIONS_PER_IP`, default `min(2, MAX_SESSIONS)`), per connection (`MAX_SESSIONS_PER_CONNECTION`, default 2) and globally (`MAX_SESSIONS`); a session keeps its lease (and the per-address slot) after a stopped search until `release` or `SESSION_IDLE_MS`.

**Decision.**
- *Setting.* `reviewEngine: 'auto' | 'browser' | 'server'` in `settingsStore` (persisted in `chesslab.settings`, default `auto`, kept by "Reset to defaults" like the token), shown in Settings below the access token. `auto`: server when one is configured (the analysis settings' `remoteUrl`, else same-origin `/ws`, i.e. `wss://c.referee.at/ws` in production) and the handshake succeeds with `capabilities.analysis !== false`; otherwise browser. `browser`: never touches the network. `server`: always tries the server first.
- *Engine per run.* `reviewStore` picks the engine at the start of every run. For the server it creates a **dedicated** `RemoteEngineClient` (own connection, one session, `hello.client.name = chesslab-web-review`, handshake 5 s — the handshake is the probe) wrapped in `ServerReviewEngine` (`apps/web/src/review/serverReviewEngine.ts`), an adapter to `Engine` that requests `threads = welcome.limits.maxThreads` and `hash = min(256, limits.maxHash)`, clamps `depth`/`movetime`/`multipv` to the limits (a preset never fails with `limit_exceeded`), and fails a search that yields nothing for 30 s (`RemoteEngineError` code `timeout`; the client itself only times out *stopped* searches). The client is disposed — `release` sent, per-address slot freed — when the run ends (done, error, cancel, reset), so the live server engines keep their quota between reviews. The browser engine stays cached as before. `BatchAnalyzer`, the presets (fast = 300 ms/move, deep = depth 18) and the classification are unchanged; on the server the same movetime simply reaches a much greater depth.
- *Fallback.* Handshake failure (unreachable, `unauthorized` / restricted welcome, timeout), a search error (`no_capacity` per-address/global cap, `limit_exceeded`, `engine_crashed`, connection closed) or the stall timeout switch the run to the browser engine: the server client is disposed and `BatchAnalyzer` runs again on the same game with the same position cache, so positions already analysed on the server are reused and only the rest is searched. The cache key is the search budget only (shared by both engines). The Review panel shows one line "Server unavailable (<reason>) — reviewing in the browser" (reasons: `not reachable`, `connection lost`, `Access token required or wrong`, `too many sessions, busy`, `no response`, `engine crashed`). Exception: in `auto`, an `unauthorized` failure (no or wrong token) falls back **silently** (no notice; the panel just says "Reviewing in browser…"), since visitors without a token would otherwise see it on every review; explicit `server` shows it. All other reasons show the notice in both modes. In `auto` a failure is remembered for 60 s per URL + token (the next review goes straight to the browser with the same notice; a new token is tried at once); explicit `server` retries every run. Cancellation never falls back.
- *UI.* Progress line "Reviewing on server (Stockfish 19, 8 threads)… / Reviewing in browser…" and, after the run, "Reviewed on server (…)." / "Reviewed in browser.". The fair-play lock (ADR-012/013) is unchanged: no review during live, engine or room games; the server additionally refuses `analyze` to a room player (`forbidden` → browser fallback, which the web lock prevents anyway).
- *Live analysis.* The review still pauses the live analysis (`setEnabled(false)`), which stops but does not release its server sessions. One live server engine + the review = 2 sessions per address, which fits the default `MAX_SESSIONS_PER_IP` of 2; with two live server engines enabled the review gets `no_capacity` and falls back to the browser (documented trade-off; no protocol change).

**Consequences.** No change to `packages/engine-core` or the WebSocket protocol. A server review costs one extra connection (within nginx's per-IP connection limits) and one session for the duration of the run; under load (`MAX_SESSIONS` exhausted) reviews degrade to the browser instead of failing. Production may want `MAX_SESSIONS_PER_IP=3` (two live server engines + review) and a `MAX_SESSIONS` that leaves room for concurrent reviews; `MAX_THREADS` is what one review gets per search.

### ADR-011 addendum (2026-10-25, M18-1)
The vendored openings table now stores `[eco, name, epd, moves]` (compact SAN line per variation, pinned upstream commit in `apps/web/src/openings/data/SOURCE.md`), ~88 kB gzip, lazily loaded with the book trie (`openings/book.ts`). The drill is move-order based (transpositions are checked by the engine, not the book); a fine non-book move before the drilled variation is reached asks for a retry, after it ends the line as "out of book".

## ADR-015 — Browser engine memory budget
**Date:** 2026-10-25 · **Status:** accepted (M19-1)

**Context.** iPad Safari reported "Stockfish worker error: RangeError: Out of memory (…/stockfish-19-lite.js:12)" again and again since the openings trainer shipped, also with the server access token set (review and drill on the server). Line 12 is `new WebAssembly.Memory({initial: 2048, maximum: 32768, shared: true})`: every `lite`/`full` instance creates a shared memory of 128 MiB with a 2 GiB maximum (`lite-single` defines the same sizes inside its `.wasm`, not shared); the build offers no option to change it (its worker bootstrap passes only `locateFile`/`instantiateWasm`). Shared memories cannot move, and WebKit reserves their maximum, so each multi-threaded instance takes a 2 GiB reservation from a limited per-page budget. Measured in headless Chromium (this VM, renderer RSS after a depth-14 search, per added instance): `lite-single` +58…67 MiB (1 worker), `lite` 1 thread +78 MiB (3 workers), 2 threads +105…115 MiB (4 workers), 4 threads +147…163 MiB (6 workers); 1/2/3 × `lite` 4T: 305/452/602 MiB renderer RSS (idle page 143 MiB), VSZ +11.3 GiB per 4T instance (V8 guard regions); everything is returned within ~8 s of `dispose`. `measureUserAgentSpecificMemory` is not available in headless Chromium here. WASM creation paths before this ADR: the live analysis (one instance per enabled browser key — up to two), the review's cached engine (created on the first browser review, i.e. also whenever `auto` fell back from the server, never disposed), a **fresh** instance per drill for its browser path, and Play vs Engine's own instance (disposed 30 s after the game). The live analysis' per-engine `Threads` override was capped only by `cores − 1` (an iPad reports 8 cores: "Threads 7", while the label said 4). A load failure was retried on every resume (review/drill/game end) and every new drill, so the error came back again and again. The server probe and the live/room locks create no WASM engine.

**Decision.**
- *Shared batch engine* (`apps/web/src/engine/wasmPool.ts`). `EnginePool` holds one browser engine (lazy create + `load`) with one lease holder at a time; later `acquire(purpose)` calls wait FIFO (`onWait` reports the holder, an `AbortSignal` cancels the wait). Released leases keep the engine; it is disposed `POOL_IDLE_MS` = 20 s after the last release, at once by `trim()`, or on `release({broken: true})` (failed engine). Before the next holder starts the pool stops the engine and applies the previous holder's `restore` options. `browserEnginePool` serves: the review (one lease per run, `setReviewEngineFactory` sets its factory, `disposeReviewEngine` disposes it), the drill's browser path (`openSearchEngine` returns a `PooledEngine` that leases per search, so a drill check waits for a running review — "Waiting for the running review to finish…", the check timeout pauses meanwhile — and the review cancels nothing), and Play vs Engine (`PooledEngine` per move; strength options re-applied per lease, `UCI_LimitStrength false` restored). The server paths are unchanged.
- *Device budget* (`engine/memoryBudget.ts`, pure). iOS/iPadOS (`iPad|iPhone|iPod` in UA/platform, or a Mac UA/`MacIntel` with `maxTouchPoints > 1`) or `deviceMemory ≤ 2` → `{maxInstances: 1, maxThreads: min(2, default), constrained: true}`, else `{maxInstances: 2, maxThreads: min(cores − 1, 4)}`. `RegistryEnv.budget` (optional; set by `currentEnv()`): `defaultThreads` and the picker labels follow it, `maxWasmThreads` caps the Threads select on constrained devices, `canEnable`/`listEngines`/`sanitizeEngineKeys` refuse/hide a browser engine beyond `maxInstances` ("Memory budget: one browser engine at a time on this device"; `lite` ⇄ `full` replacement stays allowed). `WasmEngineClient` caps `Threads` (default and `setOptions`) by the budget on constrained devices, and starts multi-threaded builds there through `engine-shim/stockfish-memory-shim.js` (shipped next to the engine files): it wraps `WebAssembly.Memory` to lower `maximum` to 8192 pages (512 MiB; Hash up to ~256 MB still fits, verified in Chromium) and `importScripts` the unchanged engine; the `.wasm` URL travels in the hash, pthreads start from the shim URL. On constrained devices pausing the live analysis (review, drill, game, live/room lock) releases its browser engines and resuming first trims the idle pool, so one WASM instance is alive at a time.
- *Failure recovery* (`engine/wasmHealth.ts`, session state). Worker `error` events, `Aborted(…)` and "Out of memory" are classified (`oom`/`worker`; timeouts are not). The first failure of a full-size instance marks the session *degraded* (all later instances use `lite-single`, 1 thread) and sets one notice (engine panel: "Browser engine restarted with 1 thread after running out of memory", dismissable); a load is retried once in place, a failure during a search returns `WasmEngineError{retryable: true}` and the consumer recreates once (AnalysisController, review run with its position cache, drill check). A failure of the degraded instance *disables* the browser engine (`retryable: false`): later loads reject without spawning a worker, the AnalysisController keeps the error over pause/resume and only the user's Retry re-allows one attempt. The review then tries the server once (setting `auto`/`server`, server configured, not already tried in this run; notice "Browser engine unavailable — reviewing on the server"), the drill likewise or ends once with "Drill ended: the browser engine is unavailable (…)."; `browser` never touches the network.
- *Observability.* `window.__chesslab.wasmInstances()` → `{live, peak, created, degraded, disabled?, pool}`, `resetWasmPeak()`; e2e `engine-memory.spec.ts` asserts peak ≤ 2 on desktop (live analysis + shared engine through a review and a drill) and peak 1 with an iPad user agent (2 threads, memory maximum 8192 pages).

**Consequences.** No change to `packages/engine-core` or the WebSocket protocol. `UciSessionOptions.onFatal` and `WasmEngineClientOptions.maxThreads`/`maxMemoryPages` are additive. On iOS a resumed live analysis reloads its engine (~0.3–1 s) and a review/drill/game reloads the batch engine after the live engine was in use; two browser engines side by side are no longer possible there. A drill check during a running review waits for the review; a review waits at most one drill search / engine move. A degraded session plays and analyses single-threaded until reload. The shim is a new file next to the pinned engine files (ADR-005 still copies the engines unchanged); nginx's `/assets/` rule covers it.

### ADR-011 addendum (2026-10-25, M18-3)
A finished engine game with at least 6 plies (counted over the whole game, including an opening line it started from) gets the automatic fast review in the background; the Review tab is not switched to automatically. The review shows an "Opening" block (name/ECO, book until ply N, who left the book with which move, book alternatives, eval swing); a move leaving the book order whose position is itself a named book position still counts as book.

## ADR-016 — Persistent review cache
**Date:** 2026-10-25 · **Status:** accepted (M20-1)

**Context.** A review was run again whenever a game was loaded or "Review" was pressed, even for a game reviewed minutes earlier (the owner: "once the review has happened there is no reason to run it again — it only costs resources"). The only cache was the review store's in-memory position cache per search budget (ADR-011/014), lost on reload and never shared between budgets, so Deep after Fast searched every position again although a Fast run on the server often reaches depth 20+.

**Decision.**
- *Game key.* `gameKey(startFen, uciMoves)` = SHA-256 hex of `chesslab-review-v1\n<startFen>\n<uci moves>` (`apps/web/src/review/reviewCache.ts`); headers, the viewed ply and SAN spelling do not matter. It is computed **synchronously** with a small pure-JS SHA-256 (`review/sha256.ts`, checked against the FIPS test vectors) rather than `crypto.subtle`: the store must decide "cached or run" before it renders `running`, `crypto.subtle` is async-only and missing on insecure origins, and one implementation gives the same key everywhere (browser, jsdom, Node). A record also stores the SAN moves and start FEN, which are compared on every hit, so a collision can only cause a miss.
- *Storage.* IndexedDB database `chesslab-reviews`, version `REVIEW_CACHE_VERSION` (1). Store `reviews` (keyPath `gameKey`, indexes `createdAt`, `preset`): `{gameKey, startFen, moves (SAN), preset 'fast'|'deep', options, summary, moveDetails, engine (ReviewEngineInfo), createdAt, version}`, at most 500 (oldest `createdAt` dropped); a weaker preset never replaces a stronger one. Store `positions` (keyPath `<optionsKey>|<fen>`, indexes `fen`, `usedAt`): `{fen, optionsKey ('mt:300' | 'd:18' …), result (eval, bestMove, pv ≤ 8, reached depth), usedAt, version}`, at most 20 000 (least recently used dropped to 90 % when exceeded). A version bump deletes and recreates both stores in `onupgradeneeded`; records of another version are ignored. No IndexedDB, a failing `open` (private mode, SecurityError, blocked, newer version in another tab) → in-memory backend with the same bounds; every storage error is swallowed (reads return nothing, writes are dropped), a cache never fails a review. A synchronous in-memory index `gameKey → strongest preset` is loaded at app start (`installAutoReview` → `warmReviewCache`) from the `preset` index (keys only).
- *Semantics (review store).* Only the two presets are cached (`presetOf`: fast = movetime 300, deep = depth 18; custom budgets of the dev hook/tests are not), and only games of ≥ 2 plies. `start(preset)`: if the shown result is already a stored review of this game with the same or a stronger preset → resolves with it, nothing changes; if the index knows a covering record → the record is loaded and shown (`status: done`, `runsOn` from the record, `stored.fromCache`), the store never enters `running`, no engine is leased, the live analysis is not paused; otherwise the run starts as before but first asks the database once (records written by another tab) before an engine is selected. `autoNotice` is shown for a cached auto review only if the stored preset is fast. A finished preset run writes the record (`stored.fromCache: false`); cancelled or failed runs write none. Navigation (`ply`) never triggers anything; a change of the `moves` array identity (load, finished game, moves entered by hand) triggers `loadCached()` after 100 ms (debounced; `installReviewCacheLookup`, installed by `installAutoReview`), which shows a stored review of any preset and never runs an engine — skipped while a review runs and during a human game (fair play).
- *Positions across budgets.* The in-memory position cache is now one map FEN → results per budget (5000 FENs LRU). A run seeds the analyzer's per-run cache with, per position, a result that `satisfies` the requested budget: the same budget; for a movetime a stored movetime ≥ requested; for a depth a stored depth limit ≥ requested **or a result whose reached depth ≥ requested** (`PositionResult.depth`, new optional field filled from the last info). Positions of every run (also cancelled/failed) are persisted at the end of the run, those of the game are loaded from the database before it. So Deep after Fast searches only positions the Fast run did not reach depth 18 in (on the server usually none or a few; in the browser most of them), and a variation sharing a prefix reuses the shared positions.
- *UI.* Review panel: after a cache hit the engine line reads "Loaded from cache (reviewed 25 Oct, deep, server)" (year added for other years); Start is disabled with "Already reviewed (deep)" while the shown review of this game covers the selected preset (so Deep stays possible after Fast). Settings → "Review cache": "N stored reviews" (updates on writes) and "Clear cache" (database, memory positions; the shown review stays but no longer counts as stored).

**Consequences.** No change to `packages/engine-core` or the WebSocket protocol; `PositionResult.depth` (web layer), `ReviewState.stored`, `ReviewActions.loadCached` and `fake-indexeddb` (dev dependency) are additive. Storage: a review record is roughly 0.5–1 kB per ply (summary + move details with SAN lines and FENs), i.e. ~30–80 kB per game, ≤ ~40 MB at the 500-record bound in the worst case (typical games far less); positions ~0.3 kB each, ≤ ~6 MB at 20 000. Records are per browser profile; a cleared site storage or private window simply reviews again. A stored review does not follow later engine/classification changes: bump `REVIEW_CACHE_VERSION` when the classification or record format changes.

## ADR-017 — Server-side review store
**Date:** 2026-10-25 · **Status:** accepted (M20-3)

**Context.** The review cache of ADR-016 is per browser profile: the same game is reviewed again on every device, and a cleared site storage or private window costs another run. The owner: "Why don't we store the analysis on the server?" The engine server already has a token-gated WebSocket with handshake, Origin check, per-IP accounting and rate limits (ADR-006/008/010/013), chess.js (ADR-013) and a game key both sides can compute (ADR-016). Disk use must be bounded and tunable for a public release (owner decision 2026-10-25: configurable via `.env`, default 5 GB). The host runs Node 24, which ships `node:sqlite` without a flag.

**Decision.**
- *Storage* (`apps/server/src/review/ReviewStore.ts`). One SQLite file (`node:sqlite`, `DatabaseSync`, WAL, `synchronous=NORMAL`) at `REVIEW_STORE_PATH` (default `apps/server/data/reviews.sqlite`, directory created; relative env paths resolve against the working directory). Tables `reviews(game_key PK, preset, start_fen, moves /* SAN joined by spaces */, record BLOB /* gzip JSON of StoredReviewRecord */, bytes, created_at, last_used)` and `positions(opts_key, fen, result BLOB /* JSON PositionResult */, bytes, last_used, PK(opts_key, fen))`, both with an index on `last_used`. **No PGN headers, player names or addresses are stored** — only moves, evaluations and the per-move details the web shows. `bytes` is the payload plus 64 bytes estimated row overhead; a running total is kept in memory (recomputed at open). When it exceeds `REVIEW_STORE_MAX_BYTES` (default 5e9; `int(1e6 … 1e13)`), least-recently-used rows are deleted down to 90 % — positions first (cheap to recompute), then whole reviews. A hit refreshes `last_used` at most once per hour. A weaker preset never overwrites a stronger one (`superseded`); the same or a stronger preset replaces the row. A record that no longer parses (incompatible server version) is deleted on read. `REVIEW_STORE=off`, a missing `node:sqlite` (Node < 22.13) or an unopenable file disable the feature with a `warn` log line — the server keeps running, `capabilities.reviewStore` is false.
- *Protocol* (additive, `PROTOCOL_VERSION` stays 1; schemas in `packages/engine-core/src/protocol.ts`, key and preset order in `reviewKey.ts`, SHA-256 in `sha256.ts` — moved from the web so both sides compute `reviewGameKey(startFen, uciMoves)` = SHA-256 of `daisychess-review-v1\n<fen>\n<uci moves>` identically). Client → server: `review.get {gameKey, startFen, moves: SAN[]}`, `review.put {gameKey, startFen, moves, preset, record: StoredReviewRecord}`, `review.positions.get {optsKey, fens ≤ 64}`, `review.positions.put {optsKey, entries ≤ 64 [{fen, result}]}`, `review.stats.get`. Server → client (exactly one answer per request, correlated by `gameKey` / `optsKey`): `review.record {gameKey, found, preset?, record?, createdAt?}` (the engine lives in `record.engine`, not duplicated at the top level), `review.stored {gameKey, stored, reason?}`, `review.positions {optsKey, results: Record<fen, PositionResult>}`, `review.positions.stored {optsKey, stored, reason?}`, `review.stats {enabled, reviews, positions, bytes, maxBytes}`. Reasons (`REVIEW_STORE_REASONS`): `unauthorized`, `disabled`, `key_mismatch`, `illegal_game`, `too_large`, `superseded`, `quota`, `storage_error`. Envelope failures stay on `error` (`rate_limited`, `invalid_message`). `welcome.capabilities` gains `reviewStore?: boolean` (absent = false). `StoredReviewRecord = {version, options, engine, summary, moveDetails}` and `StoredReview` (record + `gameKey, startFen, moves, preset, createdAt`) are defined as Zod schemas in engine-core — `ReviewSummarySchema` is checked assignable to `ReviewSummary` at compile time, the web checks its `MoveDetail`/`PositionResult` against `StoredMoveDetail`/`PositionResult` — so the server validates a record completely (every FEN with `isValidFen`, SAN with a strict pattern, UCI, bounded strings and arrays, win probabilities 0…100) and never stores or serves junk. **Frame size:** the four record-carrying types (`review.put`, `review.record`, `review.positions.put`, `review.positions`) may be up to `MAX_LARGE_MESSAGE_BYTES` = 1 MiB + 128 KiB (`ws` `maxPayload`); every other type keeps `MAX_MESSAGE_BYTES` = 16 KiB, enforced in `parseClientMessage`/`parseServerMessage` after the type is known. A record is additionally limited to `REVIEW_BOUNDS.recordMaxBytes` = 1 MiB of JSON (`too_large`); games to 2 … 1000 plies.
- *Auth split and abuse limits* (`apps/server/src/review/ReviewService.ts`, `putQuota.ts`). Reads (`review.get`, `review.positions.get`, `review.stats.get`) are open to every connection, also a restricted one (ADR-013). Writes (`review.put`, `review.positions.put`) need `capabilities.analysis === true`, i.e. the connection's `hello` carried the valid `ACCESS_TOKEN` (or the server is public) → otherwise `unauthorized`. The server **recomputes the key**: `startFen` + SAN moves are replayed with chess.js (an illegal game → `illegal_game`), the resulting UCI moves hashed and compared with `gameKey` (→ `key_mismatch`), so a record can never be stored under a foreign key; `review.get` answers `found: false` when the stored game's FEN/moves differ from the request (collision guard, now server-side). Per connection: 20 read requests/s and 20 writes per 4 s (5/s averaged, bursts of 20 — a 1000-ply game is 16 position chunks + 1 record) → `error rate_limited`, socket stays open. Per client address (`resolveClientIp`, ADR-008): `REVIEW_PUT_PER_IP_PER_DAY` (default 500) writes per UTC day, in memory per process → `quota`. Logging: `review stored`/refusals at `info` with connection id, game key (a hash of public game content) and reason; never the record.
- *Web* (`apps/web/src/server/apiConnection.ts`, `review/serverReviewStore.ts`). One shared lightweight `/ws` connection ("api") for request/response traffic: `hello` with `client.name = daisychess-web-api` and the Settings token, handshake 3 s, request timeout 10 s, correlation by reply type + `gameKey`/`optsKey`, opened on demand, closed after 60 s idle, dropped on a token/URL change; a connect or handshake failure (or `capabilities.reviewStore` false) puts it on a 60 s cooldown during which requests fail at once, so an unreachable server never delays a review. Rooms and the engine clients keep their own connections (a later refactor may move rooms onto it). Lookup order in the review store: local IndexedDB → server (`review.get`); a server hit is written to the local cache and shown exactly like a local hit, labelled "Loaded from server (reviewed 25 Oct, deep)" (`StoredReviewInfo.source: 'server'`), without entering `running` (no progress bar): for preset runs the lookup now happens before the store switches to `running`. A finished local run is written to the server silently when the connection may write (`capabilities.analysis`); failures are ignored. Positions: before a run, FENs without a local result satisfying the budget are fetched in chunks of 64 for the run's `optsKey` and, for a depth run, also for the Fast key (`mt:300`), so Deep reuses Fast positions from other devices through `satisfies`; new results are put after the run. `reviewEngine: 'browser'` never touches the network (ADR-014), so it also skips the server store. Settings → "Review cache" shows "Server: N reviews · X GB of Y GB" (`review.stats.get`) when the server offers the store.
- *Operations.* `/health/detail` gains `reviewStore {enabled, reviews, positions, bytes, maxBytes}`. The systemd unit gets `ReadWritePaths=/home/bojan/gitchess/apps/server/data` (the only writable path under `ProtectSystem=strict`/`ProtectHome=read-only`); the directory is created by the server (user `bojan`, `UMask=0077` → mode 700). The file is reproducible (reviews are recomputed on a miss): **no backup**. Docker: the server image runs Node 22 — `node:sqlite` needs ≥ 22.13; older images simply run without the store.

**Consequences.** The protocol gains ten message types and a second frame-size tier; `MAX_MESSAGE_BYTES` keeps its meaning for every existing type, but `ws` now accepts frames up to ~1.1 MiB from any connection (bounded by the 100 msg/s and the review rate limits; a `review.get` of ~200 bytes can fetch a ~1 MiB record — 20/s per connection, 10 connections per IP at nginx — accepted, see `docs/SECURITY.md`). `gzipSync`/`gunzipSync` and the Zod validation of a large record run on the event loop (≈ 1–20 ms per message; acceptable at the write rate). A format change of the record requires bumping `REVIEW_CACHE_VERSION` **and** `REVIEW_KEY_SALT` together (old records then become misses) and, because the schema lives in engine-core, deploying server and web together. `engines.node >= 20` stays; CI should move its matrix to 22/24 so the store tests (`describe.skipIf(!sqlite)`) actually run. Server unit tests that do not test the store build their apps with `REVIEW_STORE=off`, so a test run never touches `apps/server/data` (git-ignored; on the host it is the production file). `@types/node` 20 has no `node:sqlite` declarations: `apps/server/src/types/node-sqlite.d.ts` declares the subset used. The web's `sha256.ts`, `gameKey`, `covers` and `strongerPreset` are now re-exports of engine-core.

## ADR-018 — Rename to DaisyChess
**Date:** 2026-10-25 · **Status:** accepted (M21-1)

**Context.** The product owner renamed the product from ChessLab to DaisyChess, with a daisy mark (`apps/web/public/brand/`). The old name appeared in the UI, PGN headers and file names, the package scope, persisted browser state, the lichess OAuth client id, the systemd unit, nginx/fail2ban/docker names and the docs. The domain `c.referee.at` and the repository directory stay.

**Decision.**
- *UI.* Title and header read "DaisyChess"; the header shows `/brand/daisy.svg` (28 px, `alt=""`, so the heading's accessible name stays "DaisyChess"). `index.html` links `/favicon.svg`, `/brand/favicon-32.png`, `/brand/apple-touch-icon.png` and `/manifest.webmanifest` (name, icons 192/512, `display: standalone`, `background_color` = `--bg`, `theme_color` = `--surface` light), plus `theme-color` metas for light/dark (`--surface`). CSP unchanged apart from the new inline-script hash: icons are `img-src 'self'`, the manifest falls under `default-src 'self'`. nginx serves the manifest as `application/manifest+json` (explicit location; `mime.types` lacks it).
- *Names.* Package scope `@chesslab/*` → `@daisychess/*`; dev hook `window.__chesslab` → `window.__daisychess`; protocol `hello.client.name` values `chesslab-web*` → `daisychess-web*` (informational field, no schema change); PGN `Event` headers, download `daisychess-review.pgn`; lichess OAuth `client_id` `daisychess.c.referee.at`; nginx `log_format`/`limit_*` zones/CSP map variable `daisychess*`; fail2ban jail/filter `daisychess-ws`; docker images `daisychess-server`/`daisychess-web`; smoke scripts read `DAISYCHESS_TOKEN`.
- *Storage migration* (`apps/web/src/storage/migrate.ts`, run first in `main.tsx` via `storage/runMigration.ts`, before any store reads storage). Every `chesslab.*` key in localStorage and sessionStorage (`settings`, `theme`, `analysis`, `explorer`, `import.online`, `fullBuildConfirmed`, `trainer`, `play`, `nick`, `room.<id>`, `lichess`, `lichess.pkce`) is copied to `daisychess.*` unless the new key exists, then removed; a failed copy (quota) keeps the old key for the next start; idempotent and never throws. The review cache uses the new IndexedDB database `daisychess-reviews` (game-key salt `daisychess-review-v1`); the old `chesslab-reviews` is not migrated (reviews are recomputable) but deleted best-effort with `indexedDB.deleteDatabase`.
- *Server unit.* `deploy/daisychess-server.service` (same content, new description); `deploy/deploy-server.sh` stops, disables and removes an installed `chesslab-server.service` before installing the new unit. The server logs and `/health` payload carry no product name; its Fastify decorator is now `app.daisychess`.

**Consequences.** No change to the `packages/engine-core` API or the WebSocket protocol schema (only the scope name of the package and informational `client.name` strings). The lichess token survives the key migration, but lichess binds a token to its `client_id`; it keeps working until it expires or is revoked, and the next login shows the new app name ("daisychess.c.referee.at") on the lichess consent page — users may have to log in again. The theme bootstrap in `index.html` reads only `daisychess.theme`; on the first load after the update `runMigration.ts` applies the migrated theme right after the migration, so a non-system theme can flash once before the app renders. Stored reviews from before the rename are gone (one re-run per game). The live nginx site must be refreshed from `deploy/nginx/c.referee.at.conf` (new CSP hash, renamed zones/log format, manifest type) and, once fail2ban is installed (it is not yet, see `deploy/README.md`), the `daisychess-ws` jail/filter used. Historical entries in this file and in `docs/PLAN.md` keep the old name.

## ADR-019 — Human-like engine: Lc0 with the Maia networks
**Date:** 2026-10-25 · **Status:** accepted (M23-1; web M23-2/M23-3 follow)

**Context.** Stockfish answers "what is best"; the owner wants an opponent and a review hint that answer "what would a 1500 player do here" (M23). [Maia](https://github.com/CSSLab/maia-chess) (CSSLab, KDD 2020, GPL-3.0) is a set of nine Lc0 weight files trained to predict the moves lichess players of ratings 1100…1900 play; used with a 1-node search (`go nodes 1`) Lc0 returns the policy head's most probable move, and with `VerboseMoveStats` it prints the full move distribution. The production host is a 16-vCPU QEMU VM without AVX2/F16C (ADR-003) and without a GPU, so no official Lc0 binary fits (Linux builds are not published; the CPU builds assume AVX2). The engine server already has a pool with lease/idle/backoff/health handling (ADR-007/008), per-IP and per-connection caps and the access token (ADR-010/013), and a Zod protocol that may grow additively (ADR-006).

**Decision.**
- *Binary.* `scripts/build-lc0.sh` (`pnpm build-lc0`) builds Lc0 **v0.32.1** from the GitHub source tarball (sha256 pinned in the script, plus the `lczero-common` submodule at its pinned commit and digest; fail closed, `--no-verify` downgrades to a warning) with meson/ninja: CPU-only **Eigen** BLAS backend (header-only; no OpenBLAS runtime dependency or thread pool), `-Dnative_arch=false` with `-msse4.2 -mpopcnt`, `f16c`/`pext` off, no CUDA/ONNX/OpenCL/gtest, LTO. Output `engines/lc0/lc0` (2.4 MB) + `COPYING` + `VERSION` (tag, digests, flags); idempotent (same tag and flags → skip). Meson downloads abseil-cpp through its hash-verified wrap. `LC0_NATIVE_ARCH=1`/`LC0_F16C=1` exist for other hosts. Build time on the host: ~30 s wall (16 jobs).
- *Weights.* `scripts/fetch-maia.sh` (called by `scripts/fetch-engines.sh`, also when Stockfish is already present; `MAIA=off` skips) downloads `maia-1100.pb.gz` … `maia-1900.pb.gz` (~1.3 MB each, 12 MB total) from a pinned commit of CSSLab/maia-chess via raw.githubusercontent.com, verifies each against the digests pinned in the script (fail closed), checks gzip integrity and writes `engines/maia/SOURCE.md` (source, commit, authors, licence, digests). **Licence:** Maia and Lc0 are GPL-3.0 like Stockfish; both only run on the server (nothing is served to browsers), and this repository is GPL-3.0 anyway.
- *Registry* (`apps/server/engines.json`, `EngineConfigSchema`): nine entries `maia-1100` … `maia-1900` (name "Maia 1500"), each `binary: engines/lc0/lc0`, new fields `weights` (resolved like `binary`, passed as `--weights=<path>`), `args` (`--backend=eigen --threads=1 --minibatch-size=1 --max-prefetch=0 --nncache=1000`), `initOptions` (`VerboseMoveStats: true`, sent once after `uciok` by `UciProcess.start`; operator-controlled, not client-reachable), `group: "maia"`, `style: "human"`, `rating`, `maxNodes: 1`, `maxInstances: 3`. `MAIA=off` disables the group; an engine whose binary is not executable or whose weights are not readable is disabled with one warning per missing file (not nine). `UciProcess.setOptions` now skips allow-listed options the engine did not announce (Lc0 has no `Hash`; it would answer `error Unknown option`).
- *Pool.* `EnginePool` gains `groupLimits` (`{ maia: MAIA_MAX_PROCESSES }`, default 3): the live processes of all engines of a group are counted together; at the cap the least recently used **idle** instance of the group (any level) is killed before the new level spawns, and when every process of the group is leased `acquire` answers `no_capacity` ("all 3 process(es) of engine group "maia" are busy"). Idle Maia processes stay warm like Stockfish (`minWarm`, `ENGINE_IDLE_MS`); backoff, crash accounting and `/health/detail` (now with `group` per engine and `processGroups.maia {processes, max}`) are shared. Measured on the host: ~16 MB RSS per process at rest after 1-node moves, 2 threads, startup ≤ 100 ms (network load on the first `go`/`ucinewgame`), 1-node move ~1 ms median, 7 ms p90 on a warm process; a 200-node search runs at ~500 nps on one thread.
- *Protocol* (additive, `PROTOCOL_VERSION` stays 1, `packages/engine-core/src/protocol.ts`): `EngineDescriptor` gains `style?: 'strength' | 'human'` (absent = strength), `rating?` (100…4000) and `maxNodes?`; `Limits` gains `maxNodes?` (`DEFAULT_LIMITS` 10 000, env `MAX_NODES`, `PROTOCOL_BOUNDS.nodes` 1…10 000); `analyze` gains `nodes?` (`go nodes N`, combinable with `depth`/`movetime`). Semantics: `checkAnalyzeLimits` reports `nodes` above `limits.maxNodes` — and, when `limits.maxNodes` is absent (a server older than this ADR, which would strip the field), "nodes is not supported by this server"; `resolveEngineNodes(msg, engine)`: an engine with `maxNodes` runs exactly `maxNodes` when the client sends none and rejects more with `limit_exceeded` (so a Maia engine never searches, whatever the client asks). `EngineInfo`/`EngineInfoSchema` gain `policy?: PolicyEntry[]` (`{ uci, p }`, `p` a fraction 0…1, most probable first, ≤ 10 entries). `parseLc0MoveStats(line)` parses one `info string <move> (<idx>) N: … (P: 50.22%) …` line (Lc0's root summary `info string node …` and every other line give null), `topPolicy(entries, n)` sorts; `UciProcess` collects the lines of the running search and returns `SearchResult.policy` (top 5) with the `bestmove`; the connection then sends **one more `info`** — the last relayed info of that search plus `policy` — immediately before `bestmove`. If no `info` was relayed (Lc0 prints none on a checkmated/stalemated position) nothing is added. `parseUciBestMove` maps the null moves `0000`/`a1a1` (Lc0's answer on a terminal position) to `null`, so the client never receives an unplayable move.
- *Limits and abuse.* Unchanged by design: Maia sessions are ordinary sessions (per-connection, per-IP and global caps, 20 `analyze`/s, token required, `forbidden` while playing in a room). A Maia `analyze` costs one network evaluation (~1 ms CPU); the expensive path (`nodes` up to 10 000 on Stockfish, or a Maia entry re-configured with a larger `maxNodes`) stays bounded by `MAX_NODES` and the wall-clock cap.
- *Deployment.* `deploy/deploy-server.sh` runs `pnpm fetch-engines` and `pnpm build-lc0` (both idempotent). No systemd change: binary and weights are read from the read-only `/home` mount, Lc0 needs only `@system-service` syscalls and 2 threads per process. `.env.example` documents `MAIA`, `MAIA_MAX_PROCESSES`, `MAX_NODES`. Docker is not updated (open point below).

**Consequences.** Clients that know this ADR pick human-like engines by `style === 'human'` and show `rating`; older clients see nine more engines named "Maia …" that behave like 1-node engines (they ignore `style`, send no `nodes`, and get the policy move with one `info` carrying `policy`, which they strip). Every `welcome.limits` now carries `maxNodes`, and `DEFAULT_LIMITS` changed (tests comparing limits literally were updated). `EngineConfig` has three new required-with-default fields (`args`, `initOptions`, `style`); code that builds configs by hand (tests) must supply them. The build adds `meson`/`libeigen3-dev` to the host's build dependencies and a network-dependent step to the deploy; a Lc0 or Maia upgrade means changing the pinned tag/commit **and** the digests in the two scripts. Open: Docker image (`docker/server.Dockerfile`) does not build Lc0 yet — Maia entries are simply disabled there; the web (M23-2/3) decides how to present `policy` and how to pick a rating from PGN headers.

## ADR-020 — Community engine nodes and hub
**Date:** 2026-10-25 · **Status:** proposed (design, M24-0; implementation M24-1 … M24-15; five product questions at the end)

**Context.** The owner wants to offer DaisyChess to the community (GPL-3.0, public repo, M25) and later as iOS/Android apps (M26). Server analysis today means *one* engine server (this host, 16 vCPU without AVX2, ADR-003) behind *one* shared `ACCESS_TOKEN` (ADR-010/013). That does not scale to strangers: the owner cannot donate 16 cores to the internet, and people who own a fast machine cannot lend it to their friends without exposing a WebSocket, running TLS, and handing out a shared secret. Decisions of 2026-10-25: anyone may run a DaisyChess **node** (Node.js or Docker, with the engines) that registers with the owner's **hub** (c.referee.at); for a player the service is transparent — the app needs only a **token**, the hub works out from the token where the engine lives. Nodes can be **private** (serve only the tokens their operator issued) and/or join a **shared pool** (donated capacity for players without a node); operators manage their nodes and issue, name and revoke player tokens in a small **operator portal**; players never need an account; nodes + hub first, apps afterwards.

What exists and must be reused: the ADR-006 protocol (`hello{token}` → `welcome{engines, limits, capabilities}`, sessions, searches, `info`/`bestmove`/`error`), `apps/server` (`EnginePool`, `UciProcess`, registry, `Connection` with its session/search state machine, per-IP ledger, rate limits, rooms, review store), the Origin policy (ADR-008), the hardening of the unit/Docker image (`docs/SECURITY.md`), the verified engine downloads and the Lc0 build (ADR-019), `node:sqlite` on the host (ADR-017), and the web client's token handling (`hello.token`, Settings, setup link, M23-4). The production service must keep working for the owner's devices throughout.

**Decision.**

### 1. Topology: outbound node link, hub relays (v1); direct mode deferred

- A node opens **one outbound WebSocket** to the hub (`wss://c.referee.at/link`, nginx → `127.0.0.1:8580`), authenticates with its node token in the first frame, and keeps the link open (heartbeat, reconnect with backoff). Nothing listens on the node; it works behind NAT, CGNAT, home routers and corporate firewalls, needs no TLS certificate, no DNS name and no port forwarding. That is the single biggest adoption factor for "anyone can run a node".
- The hub **relays** analysis traffic: a player's connection stays with the hub exactly as today (same origin, same `/ws`, same CSP `connect-src wss://c.referee.at`), the hub forwards the player's `analyze`/`stop`/`release` to the routed node and the node's `info`/`bestmove`/`error` back, **multiplexing every player connection of that node over its one link** (envelope `{cid, msg}`, §3). Cost: one extra hop (10–50 ms on top of the engine's own latency; `info` cadence is unaffected) and hub bandwidth (an `info` frame is 150–400 bytes; a search streams 5–50 of them per second → ≤ 20 kB/s per running search; 100 concurrent searches are ~2 MB/s, well within the host). Benefits: the hub sees and enforces every limit (per IP, per token, per node), nodes never learn client IPs, no node ever needs to be reachable, the web app and its CSP do not change, and a node can be replaced underneath a player.
- **Direct mode** (hub returns the node's public `wss://` URL and the client connects there) is **deferred**: it needs TLS + a hostname on the node, per-node CSP `connect-src` entries (impossible for a static policy; apps in M26 have no CSP problem, which is why it stays on the table), exposes node addresses to players, and the hub loses visibility of the traffic it is supposed to police. The link protocol reserves `node.hello.publicUrl` for it; nothing else in this ADR depends on relay vs. direct.
- **Which services live where.** Central on the hub: the static web app, friend rooms (ADR-013; token-less, in memory), the review store (ADR-017; reads open, writes with any valid token), the token registry and routing, the operator portal, abuse accounting and logs. On nodes: every engine session — Stockfish analysis, Maia (`style: human`), and the review's searches (a review *is* a session, ADR-014; its results are still written to the hub's store by the client, so a Deep review on a community node benefits everybody). lichess login, explorer and import are browser-side and unchanged. The hub's own engines (this host) become the hub's **built-in node** (`local`): same code path as a remote node, in-process instead of over a link.

### 2. Identity and tokens

- **Operators log in with lichess** (OAuth 2.0 PKCE, public client `daisychess-portal.c.referee.at`, scope-less). Evaluated against e-mail magic links: a magic link needs an outbound mail path, deliverability and spam handling, stores e-mail addresses (personal data under the GDPR, with the retention/deletion duties that brings) and is trivially farmed; lichess identity costs nothing to operate, the audience already has it, it gives a stable public name for reputation ("node *fast-box* by *bojan*"), and the web app already contains the PKCE flow (ADR-012). The hub stores only the lichess user id and username. GitHub login can be added later as a second provider behind the same `operators` row. The PKCE exchange runs in the portal SPA (reusing `apps/web/src/lichess/auth.ts`), which then `POST`s the lichess access token to the hub once; the hub verifies it with `GET https://lichess.org/api/account`, creates its own session, **discards the lichess token** and the SPA revokes it (`DELETE /api/token`). The hub therefore needs exactly one outbound call per login; the unit's `IPAddressDeny=any` stays, and the call goes through an nginx **loopback egress proxy** (`listen 127.0.0.1:8581`, `location = /api/account { proxy_pass https://lichess.org; }`) rather than opening egress for the whole process. The first login of `HUB_ADMIN_LICHESS=<username>` is the hub administrator (sees every node, pool settings, suspect flags).
- **Node credential: node token**, minted in the portal when a node is created: `dcn_<nodeId>_<secret>` (`nodeId` 8 chars base32, `secret` 32 chars base32 = 160 random bits), shown once. At rest the hub keeps `sha256(secret)` (the secret has ≥ 128 bits of entropy, so a fast hash is correct here; no salted KDF needed). **Rotation:** "Rotate" issues a new secret and keeps the previous one valid for 24 h (`secret_hash_prev`, `prev_expires_at`) so an operator can update the node's environment without a gap; **revocation** is immediate — the hub closes the link (`link.close {reason: 'revoked'}`) and routes nothing to it. A keypair (node signs its frames) was considered and rejected for v1: TLS already authenticates the link, and a signature proves *who* computed a result, not *whether it is right* (§5 handles that).
- **Player ("user") tokens** are opaque: `dc1_<tokenId>_<secret>` (prefix = format version; `tokenId` 8 chars base32, public, used in logs, the portal and error messages; `secret` 32 chars base32). The hub looks the row up **by `tokenId`** and compares `sha256(secret)` in constant time (`tokenMatches`). The routing target is **not** encoded in the token: a token's nodes can be changed in the portal (operator moves users to a new machine) without re-issuing, and the token does not reveal which node someone uses. Each token carries: `operatorId`, `label` (operator-chosen name, e.g. "Anna's iPad"), `nodeIds[]` (ordered preference; may be empty for a pool-only token), `poolFallback: boolean` (use the pool when every listed node is offline or full), `tier` (`small` = 1 session / 2 threads / 60 s movetime, `standard` = 2 sessions / node's threads / 10 min, `full` = the node's limits; the effective `welcome.limits` is the element-wise minimum of the tier and the node), `expiresAt?` (default: none for private tokens, 90 days for pool tokens), `revokedAt?`, `lastUsedAt`, `uses`. Tokens are shown once at creation; the portal lists `tokenId`, label, scope, last use and a "revoke" button. Revoking closes the token's open connections at once. `MAX_TOKEN_LENGTH` (256) and the `hello.token` field are unchanged, so old clients carry new tokens without a change.
- **Pool tokens.** v1: pool access is granted by tokens whose `nodeIds` is empty or whose `poolFallback` is set — issued by any operator (an operator who donates a node may also issue pool tokens for friends; capped at `POOL_TOKENS_PER_OPERATOR`, default 50) and by the administrator. The `tokens.kind` column (`user | pool | anonymous`) already reserves **anonymous per-device tokens** (minted by the hub on request, `small` tier, short expiry, per-IP minting rate) for the apps and a possible "try the pool without a token" mode; whether to switch that on is product question 1 and is behind `POOL_ANONYMOUS=on` (default off).
- **Today's `ACCESS_TOKEN` keeps working** (migration, no change on the owner's devices): a hub with `ACCESS_TOKEN` set treats a `hello.token` equal to it (constant time, as now) as a `full`-tier token bound to the built-in node `local`, with no pool fallback. It is logged as `tokenId: 'legacy'`. The owner can later mint `dc1_` tokens for each device and unset `ACCESS_TOKEN`.

### 3. Protocols

**Player ↔ hub: unchanged, two additive fields.** `PROTOCOL_VERSION` stays 1. The hub answers `hello{token}` with a `welcome` it composes from the routed node: `engines` = the node's descriptors, `limits` = min(tier, node limits), `capabilities` as today (`analysis`, `rooms: true`, `reviewStore`). Additive, optional: `welcome.node?: { name: string; operator?: string; shared: boolean }` (so the UI can say "Analysing on *fast-box* (community node by bojan)"), and `welcome.analysisDenied?: 'no_token' | 'bad_token' | 'expired' | 'revoked' | 'node_offline' | 'no_capacity'` sent together with the restricted welcome (`capabilities.analysis: false`, `engines: []`) so the client can say *why* instead of "token required or wrong". Everything after the handshake — `analyze`, `stop`, `release`, `info`, `bestmove`, `error`, rate limits, `no_capacity`, `limit_exceeded` — keeps its meaning; the hub checks `checkAnalyzeLimits` against the composed limits *before* relaying (so a node is never bothered with an over-limit request), and the node checks again against its own limits (defence in depth: a compromised hub cannot push more than the operator allowed). A connection is routed **once, at `hello`** (all sessions of a connection go to one node, so the engine list in `welcome` is consistent); when its node goes away mid-connection the hub ends every running search of that connection with `error engine_crashed` (existing semantics: session released, search terminated) and then closes the connection with WebSocket code **1012 (service restart)**; the client reconnects and gets a fresh `welcome` from whichever node is routed then. There is no transparent mid-search migration (search state lives in the engine process); a review simply retries the position (ADR-014 already treats `engine_crashed` as a fallback trigger — M24-11 makes it reconnect to the server once before dropping to the browser).

**Node ↔ hub link** (`packages/engine-core/src/link.ts`, Zod, no Node/DOM; `LINK_PROTOCOL_VERSION = 1`, independent of the player protocol; frames ≤ `MAX_LINK_MESSAGE_BYTES` = 20 KiB = a player frame plus envelope; JSON text, one message per frame):

| Direction | Message | Meaning |
|---|---|---|
| node → hub | `node.hello {linkVersion, nodeToken, node: {version, platform, arch}, engines: EngineDescriptor[], limits: Limits, maxSessions, pool: boolean, publicUrl?}` | First frame within 10 s, or the hub closes 1008. `engines`/`limits` are exactly what the node would put in its own `welcome`. `pool` is the node's own switch (`POOL=on`); the effective pool membership is `pool && portal setting`. |
| hub → node | `node.welcome {hubVersion, nodeId, name, pool: boolean, heartbeatMs, minNodeVersion, latestNodeVersion}` or `node.error {code: 'bad_token' | 'revoked' | 'link_version' | 'node_outdated' | 'replaced' | 'rate_limited'}` + close | `replaced`: the same node id connected again (a second process with the same token) — the newer link wins, the older is closed. `node_outdated`: `node.version < NODE_MIN_VERSION`. |
| node → hub | `node.status {sessions, maxSessions, load1, engines: [{id, busy, idle, degraded}]}` | Every `heartbeatMs` (10 s) and whenever `sessions` changes; the scheduler's input. WebSocket ping/pong (`ws`) detects dead links; two missed pongs → link dropped. |
| hub → node | `client.open {cid, limits: Limits, label?: string}` | A routed player connection; `cid` is hub-assigned, unique per link, never the token or the IP. `limits` are the composed limits the node must enforce for this client (≤ its own). |
| hub → node | `client.msg {cid, msg: AnalyzeMessage | StopMessage | ReleaseMessage}` | Relayed verbatim after hub-side validation. |
| node → hub | `client.msg {cid, msg: InfoMessage | BestMoveMessage | ErrorMessage}` | Relayed verbatim to the player after validation (`ServerMessageSchema`). Session-level and search-level errors keep their ids; a connection-level `error` (no `sessionId`) from a node is **not** relayed (it would mean the node is confused about a client) and is logged. |
| hub → node | `client.close {cid}` | The player disconnected or was re-routed: the node stops and releases every session of `cid`. Idempotent. |
| node → hub | `client.closed {cid}` | Optional acknowledgement once the node dropped its leases (lets the hub free the per-IP slots exactly, as `Connection.whenClosed` does today). |
| node → hub | `node.drain {reason}` | The node wants to stop (SIGTERM, update): the hub routes no new connections to it, waits up to `DRAIN_MS` (30 s) for running searches, then the node closes the link. Running searches past the deadline get `engine_crashed`. |
| hub → node | `link.close {reason: 'revoked' | 'shutdown' | 'replaced' | 'rate_limited'}` | The hub is about to close the link. |

Semantics the node side must keep: every accepted search still ends with exactly one terminal message, ordering per session is preserved (the node runs the existing session chain per `cid`), and `(cid, sessionId)` is the node's session key — `sessionId` stays client-chosen and scoped to the player's connection, so nothing in the player protocol changes. **Backpressure:** the node drops `info` (never terminal messages) for a `cid` when its link socket buffers more than 1 MiB, and additionally caps `info` at 60 per second per search so one chatty engine cannot crowd the link; the hub applies today's per-player-socket rule when forwarding. **Rate limits on the link:** at most `LINK_MAX_MSGS_PER_S` (default 5 000) frames per second from a node, `client.msg` for an unknown `cid` is ignored and counted (100 in a minute → `rate_limited` close), a frame over 20 KiB closes the link. **Version negotiation:** `linkVersion` must equal the hub's (`link_version` → the node prints "update @daisychess/node"), `minNodeVersion` in `node.welcome` lets the hub ask for an update while still serving, `NODE_MIN_VERSION` on the hub rejects nodes that are too old. **Reconnect:** the node retries with exponential backoff 1 s → 60 s, ±20 % jitter, forever; a `bad_token`/`revoked`/`node_outdated` answer stops the retries and exits non-zero (so Docker's restart policy does not hammer the hub). Nodes send no `Origin` header, so the ADR-008 Origin policy does not apply to `/link`; the node token is the authentication.

### 4. Routing and scheduling (hub)

1. `hello` without a token → restricted welcome `analysisDenied: 'no_token'` (rooms and review reads work as today). With a token: legacy `ACCESS_TOKEN` → node `local`; `dc1_` → lookup by `tokenId`; unknown id or wrong secret → `bad_token`; `revokedAt`/`expiresAt` → `revoked`/`expired`. A per-IP failure counter (20 bad tokens in 10 min → `rate_limited` and close) stops guessing, on top of nginx's handshake limit.
2. **Private routing:** the first node in `nodeIds` that is online, not draining, not `suspect`-removed, and has a free session slot gets the connection. None available and `poolFallback` → step 3; otherwise `analysisDenied: 'node_offline'` (restricted welcome, socket stays open for rooms/review reads; the client shows "Your engine node *fast-box* is offline").
3. **Pool scheduling:** candidates are online pool nodes with `poolSessions < poolShare` (operator-set share of `maxSessions` donated to the pool; private tokens of that operator may use the whole node) and no degraded engine for the requested style. Score = free pool slots ÷ `poolShare` (relative load, so a 2-slot laptop and a 32-slot server fill proportionally), tie-break by link RTT (hub-measured pong latency) and a recent-failure penalty (crash/`engine_crashed` on that node in the last 10 min). **Sticky:** a token prefers the node it used in the last 10 minutes (keeps a reconnecting review on the same engine list). No queueing: no candidate → `analysisDenied: 'no_capacity'` at `hello`, `error no_capacity` on a later `analyze` when the node filled up meanwhile (clients already show "Server busy, try again").
4. **Fairness and caps:** per token `tier.sessions` across all of the token's connections (a `TokenSessionLedger`, the sibling of `IpSessionLedger`); per IP `MAX_SESSIONS_PER_IP` as today, counted by the hub across all nodes; per node `maxSessions` (node-reported) and `poolShare`; per operator `POOL_TOKENS_PER_OPERATOR`. `anonymous` tokens (if enabled) additionally get a daily engine-time budget (`ANON_DAILY_SECONDS`, default 1 800) accounted from `bestmove` timestamps.
5. **Failover:** node loss → §3 (`engine_crashed` + close 1012); the hub marks the node offline, keeps its row, and its tokens fall back per their settings on the next `hello`. The built-in node `local` is scheduled like any other (the owner's tokens list it; its `poolShare` is a hub setting, default 2 of `MAX_SESSIONS`).

### 5. Security and abuse (threat-model delta in `docs/SECURITY.md` §6)

- **Operators see positions.** Every FEN a player analyses on a community node is visible to that node's operator (and nothing else: no IP, no PGN headers, no names, no token). The app shows a one-time notice before the first search on a node the player's token did not list explicitly (pool) and names the node and operator in the engine status; `docs/PRIVACY.md` says the same. Game review records in the hub's store are, as before, public content (moves + evaluations).
- **Malicious or broken nodes (wrong results).** Signing is useless against this (see §2). Three layers: (1) *validation* — everything a node sends passes `ServerMessageSchema`/`link.ts`, so a node cannot send off-contract or oversized frames, unknown ids or connection-level errors to players; (2) *spot-checks* — the hub re-runs a random sample of pool searches on its built-in node (`SPOTCHECK_RATE`, default 0.5 % of searches with depth ≥ 10, only when `local` is idle, ≤ 1 % of its CPU) and compares `bestmove` and score (same best move, or score within 50 cp / same mate sign); three disagreements within 24 h mark the node `suspect`: removed from the pool, flagged to its operator and the administrator in the portal, private tokens keep working (their users chose that operator); (3) *reputation* — nodes are tied to lichess identities, players see the node name and operator, and the administrator can ban a node or operator. Engine *names* are node-reported and displayed as such.
- **Node → hub.** A node can only address the `cid`s the hub gave it; it never sees tokens or IPs; link rate limits and the 20 KiB frame cap bound what it can push; a node that floods is closed and backs off. A node cannot influence routing beyond its own `maxSessions`/`pool` flags (an inflated `maxSessions` only hurts that node's users).
- **Hub → node.** The node validates every relayed message with the same engine-core schemas and the same allow-listed UCI options as today (`Threads`, `Hash`, `MultiPV`), spawns engines from its own `engines.json` only, and enforces its own limits — a compromised hub gets exactly what an anonymous player gets today, nothing more. The node needs no inbound port; the Docker image runs read-only, non-root, `cap_drop ALL`, no `--privileged`; `HUB_URL` must be `wss://` (plain `ws://` only with `DAISYCHESS_INSECURE=1`, for development).
- **Hub DoS / amplification.** `/link` is behind nginx `limit_req` (2 handshakes/s per IP, burst 5) and `limit_conn 5`; the first frame must be a valid `node.hello` within 10 s; a bad node token closes 1008 and is counted per IP (fail2ban filter extended to `/link`). Node reconnect storms are bounded by the node-side backoff. Player-side amplification is unchanged from today (per-IP session cap, rate limits), with the hub as the only relay point.
- **Token leakage.** Tokens are shown once, hashed at rest, never logged (only `tokenId`), never in URLs (the setup link `#setup-token=` keeps its fragment-only trade-off, SECURITY.md §2.10); revocation is one click and immediate; the portal shows `lastUsedAt` and open connections per token so leaks are noticeable; pool tokens expire by default.
- **Portal.** Session cookie `__Host-daisychess_portal` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`), every mutating request additionally needs `X-Requested-With: daisychess-portal` (no cross-site form can send it), REST under `/api/portal/*` on the same origin, rate-limited per session and per IP, no HTML rendering on the hub (the SPA is static under `/portal/` with the site's CSP). Operators see only their own nodes/tokens; the administrator sees aggregates and flags, never secrets.
- **Logging without PII.** Hub logs carry `tokenId`, `nodeId`, `cid`, connection id and — at `info` — a **daily-salted hash** of the client IP (raw IPs only at `debug`), which closes M10-2; FENs stay at `debug`. journald retention on the host is set to 7 days (`SystemMaxUse`, `MaxRetentionSec`). Nodes log `cid`s and engine events, never positions above `debug`.
- **GDPR / ToS.** Personal data held by the hub: operators' lichess id + username (account deletion in the portal removes operator, nodes and tokens), token labels (operator-chosen; the portal says not to put real names in them), hashed IPs in short-lived logs. No e-mail addresses. `docs/TERMS.md` (operators: you run GPL software on your hardware, no uptime obligation either way, the hub may remove nodes, pool contributions are voluntary and unpaid) and `docs/PRIVACY.md` (players: positions go to the node named in the app; nothing else) are linked from the portal and the app. The review store's existing position data is unchanged.

### 7. Packaging

- **One codebase, three roles.** `apps/server` gets `ROLE=standalone | hub | node` (default `standalone` = today, so self-hosters and the Docker compose of M6 are untouched). `hub` = standalone + `/link` + router + hub store + portal API, its own pool registered as node `local`. `node` = pool + outbound link, no public listener (loopback `/health` only). This beats a separate `apps/hub`: the node *is* 80 % of the existing server (pool, process wrapper, registry, verified engine fetch, hardening), the hub *is* the existing server plus a router, and one test suite covers all three.
- **Docker** (`docker/server.Dockerfile`, image `daisychess-server`, published to `ghcr.io/<owner>/daisychess-server` on tags): **multi-arch amd64 + arm64** via buildx in GitHub Actions (arm64 on the native `ubuntu-24.04-arm` runner, no QEMU). Stockfish: amd64 keeps the verified release asset (the sf_19 *universal* build picks SSE4.1/AVX2/AVX-512 at runtime — no AVX2 detection needed in the image); arm64 builds the pinned, sha256-verified source tag with `ARCH=armv8` (no official Linux arm64 asset). Lc0 + Maia are built into both images from the pinned sources of ADR-019 (Eigen backend; on arm64 NEON) so pool nodes offer `style: human` too; `MAIA=off` or a tiny machine disables them. `docker/docker-compose.node.yml`: `ROLE=node`, `HUB_URL`, `NODE_TOKEN`, `POOL`, `MAX_SESSIONS`, `MAX_THREADS`, `MAX_HASH_MB`, `cpus`/`mem_limit` examples; read-only, non-root, no ports.
- **npm:** `apps/node` = `@daisychess/node` (the only published package; `bin: daisychess-node`; built with esbuild into one `dist/cli.mjs` so `npx -y @daisychess/node` needs nothing else; Node ≥ 20). First run fetches the verified Stockfish release for the host (a Node port of `scripts/fetch-engines.sh`: GitHub release digest + pinned sha256, same fail-closed rules) into `DAISYCHESS_HOME` (default `~/.daisychess`); Lc0/Maia only when `--engines-dir` points at an existing build (no compiler toolchain assumptions on `npx` users). Config: `HUB_URL`, `NODE_TOKEN`, `POOL=on|off`, `MAX_*`, `MAIA`, `ENGINES_CONFIG`, `LOG_LEVEL`; flags mirror the env.
- **Auto-update policy:** no self-update. The node reports its version; `node.welcome.latestNodeVersion` makes it log "a newer node is available" once per day, `minNodeVersion` makes the hub refuse incompatible nodes with a clear message. Docker users pin or follow `:latest`; `npx -y @daisychess/node@latest` resolves the current version on each start. Link-protocol changes bump `LINK_PROTOCOL_VERSION` and `NODE_MIN_VERSION` together.

### 9. Migration of the production server (owner's devices keep working)

1. Deploy `ROLE=hub` with the existing `.env.production` (`ACCESS_TOKEN` still set → legacy route to `local`); the hub store is created on start; nginx gains `/link` (graceful `reload`). The only interruption is the same ~2 s service restart every deploy has had; no device needs a new token or setting.
2. Owner logs into the portal with lichess (`HUB_ADMIN_LICHESS`), sees node `local`, mints a `dc1_` token per device at leisure (the setup link of M23-4 works for them), and unsets `ACCESS_TOKEN` when every device has one.
3. First community node: Docker image on another machine with a node token from the portal; `pool_share` set in the portal; the owner's own tokens list `local` first and may enable `poolFallback`.
4. Roll-back at every step: `ROLE=standalone` (or unset) restores today's server; the hub store file is simply ignored.

**Consequences.**
- The player protocol is untouched except two optional `welcome` fields; today's web build and every third-party client keep working against the hub, and the hub against a standalone server. The link protocol is a new, separately versioned contract in engine-core.
- `ws/connection.ts` is refactored (M24-1) before any hub code lands; its tests (`ws.test.ts`, `rooms.test.ts`, `review.test.ts`) are the regression net and must pass unchanged.
- The hub becomes stateful (operators, nodes, tokens): backups and a schema-migration path are new operational duties; the review store stays disposable.
- Pool quality is bounded by spot-checks and reputation, not guaranteed; the UI must always say where a search runs. Players on pool nodes accept that an operator sees their positions.
- Relay doubles hub bandwidth per search (in from the node, out to the player) and adds a hop; the hub's event loop does JSON parse + validate twice per relayed frame (~10–30 µs), fine for thousands of frames per second; if the pool outgrows one host, direct mode (reserved `publicUrl`) or a second hub are the next steps.
- Two new deployable units (portal SPA, node CLI) and a release workflow; the npm package name `@daisychess/node` must be claimed before M24-13.
- Open until implemented: exact nginx rate values for `/link`, the `small/standard/full` tier numbers (operator-adjustable later), and whether `review.put` from pool tokens needs its own quota (today the per-IP daily cap applies).

**Open questions for the owner (product level).**
1. **Anonymous pool access:** should the app/web let a visitor use the pool *without* a token (hub-minted per-device token, `small` tier, daily engine-time budget), or is the pool only reachable through operator-issued tokens at launch? (Recommendation: operator-issued only at launch; anonymous behind `POOL_ANONYMOUS` for the apps.)
2. **Operator login:** lichess OAuth only (recommended), accepting that operators need a lichess account? GitHub as a second provider later?
3. **Hub domain:** stay on `c.referee.at` for hub, portal (`/portal/`) and link, or move to a dedicated domain before the public release? (Affects the OAuth client id, CSP, setup links and every node's `HUB_URL`; cheapest to decide now.)
4. **Pool fairness:** unlimited while capacity exists (first come, first served, per-token session caps only), or a daily engine-time budget per pool token (e.g. 30 min) so a few heavy reviewers cannot drain donated capacity?
5. **Release scope:** Docker node image first and the `npx @daisychess/node` package after the first community nodes run (recommended), or both before announcing?

### ADR-020 — implementation clarifications of the link protocol and tokens (M24-2, 2026-10-25)
Fixed by `packages/engine-core/src/link.ts`, `tokens.ts` and the additive `welcome` fields in `protocol.ts`; where this differs from §2–§4 above, this section wins.
1. **No large-message tier on the link.** The review store (ADR-017) and rooms (ADR-013) stay on the hub; only the analysis subset is relayed — hub → node `client.msg.msg ∈ analyze | stop | release`, node → hub `client.msg.msg ∈ info | bestmove | error` — so a link frame is a player frame (16 KiB) plus the envelope and `MAX_LINK_MESSAGE_BYTES` = 20 KiB is a single hard cap (UTF-8 bytes, `utf8ByteLength`). A node `error` without `sessionId` fails the schema (a node has nothing to say about a player's *connection*), so the hub never has to decide whether to relay one.
2. **`client.open {cid, limits, shared, tier, tokenId?, label?}`.** `shared` says whether the connection came through the pool; `tokenId` (public id) and `label` are present **only on private routes** (the token belongs to the node's operator) and the schema rejects a pool route that carries them — a pool node learns nothing about the player beyond its positions. `tier` (`small | standard | full`, `TOKEN_TIERS`) is informational; the tier→limits numbers remain hub policy and are not part of the protocol.
3. **`node.welcome` additionally carries `linkVersion` and `drainMs`** (the hub's drain deadline, default 30 s), so the node needs no configuration of its own for either. `node.error.message` is required; `node.error` gains `invalid_message` (first frame was not a valid `node.hello`). `link.close {reason, code, message?}` names the WebSocket close code the hub closes with. `node.drain.reason ∈ shutdown | update`.
4. **Fatal link ends** (`LINK_FATAL_ENDS`, `isFatalLinkEnd`): `bad_token`, `revoked`, `link_version`, `node_outdated` *and* `replaced` stop the node's retries and make it exit non-zero — a second process with the same token is an operator error that must become visible rather than two processes replacing each other forever (Docker's restart backoff bounds the flapping). `rate_limited`, `invalid_message` and `shutdown` reconnect with backoff.
5. **Version negotiation helpers:** `checkLinkCompatibility(hello, {minNodeVersion, linkVersion?})` (hub; `link_version` before `node_outdated`), `nodeVersionStatus(own, welcome)` (node: `outdated | update_available | current`), `compareVersions` (numeric `major.minor.patch`, pre-release sorts before the release). Versions must match `VersionSchema` (`\d+.\d+.\d+[-pre]`).
6. **Token alphabet:** lowercase RFC 4648 base32 (`a-z2-7`), case-sensitive, fixed length 45 (`dc1_`/`dcn_` + 8 + `_` + 32); `parseToken` is strict (no trimming, no case folding) and `isLegacyToken` is true only for a non-empty token without a reserved prefix — a legacy `ACCESS_TOKEN` must therefore not start with `dc1_`/`dcn_`, and a prefixed but malformed token is `bad_token`, never legacy. `node.hello.nodeToken` is schema-validated as a string only; the hub answers `bad_token` when `parseToken` returns null. Hashing (`sha256` of the secret) and constant-time comparison stay on the server.
7. **`welcome.analysisDenied` gains `budget_exhausted`** (owner answer 4: daily pool engine-time budget). When the budget runs out *during* a connection the hub answers the next `analyze` with the existing `error no_capacity` and an explanatory message — no new player-protocol error code, so third-party clients built against protocol 1 keep working; the precise reason appears on the next `hello`.
8. `sideEffects: false` is set on `@daisychess/engine-core`; the web bundle does not contain the link module (verified: no link strings in `dist/assets`, main chunk +234 bytes for the two `welcome` fields). Zod's `jitless` configuration keeps running first (it is a web-side module, evaluated before any engine-core import).

### ADR-020 — relay layering (M24-5): `AnalysisChannel`, `RelaySessions`, accounting on the hub
**Date:** 2026-10-25 · **Status:** accepted (design follow-up of M24-1; implemented by M24-3/5/6)

**Context.** M24-1 extracted the session/search/lease state machine into `sessions/ClientSessions.ts` and gave it an `AnalysisBackend` seam (`acquire`/`release` of one engine per session, UCI-like `BackendEngine`). ADR-020 §3 however relays *player messages* (`client.msg {cid, msg}`) and lets the **node** run `ClientSessions` per `cid`. A `RemoteNodeBackend` implementing `AnalysisBackend` (as §8 sketched) would make hub and node both run the state machine — twice the ordering/terminal logic, two idle timers, and the hub would have to invent a `BackendEngine` out of relayed frames. The seam the hub needs is one level up: a *message channel*, not an engine lease. Four sub-questions came with it: (a) hub-side per-IP/per-token session accounting without leases, (b) exactly one terminal message per open search on node loss, (c) the node's `ClientSessions` without client IPs, (d) where the daily pool budget is metered.

**Decision.**

1. **Seam = `AnalysisChannel`** (`apps/server/src/sessions/AnalysisChannel.ts`). `Connection` depends on it, not on `ClientSessions`; two implementations: `ClientSessions` (local engines; unchanged, gains `implements AnalysisChannel`) and `RelaySessions` (hub → node over a link). `AnalysisBackend`/`LocalBackend` stay as the lease seam *inside* `ClientSessions` only; **`RemoteNodeBackend` is dropped** (§8 of ADR-020 is superseded here).
   ```ts
   interface AnalysisChannel {
     readonly sessionCount: number;            // open sessions (for /health and tests)
     handle(msg: AnalyzeMessage | StopMessage | ReleaseMessage): void;
     retireAll(): void;                        // fair play (ADR-013): drop every session
     close(): Promise<void>;                   // idempotent; nothing delivered afterwards
   }
   ```
2. **Routing happens at `hello`, so the channel is created at `hello`.** `ConnectionOptions` gets an `AnalysisRouter` instead of `backend/limits/engines/accessToken`; the channel is `null` until routed (`analyze` → `unauthorized` as today) and `welcome` is composed from the route (`limits`, `engines`, `node`, or `analysisDenied`). Standalone ships a `LocalRouter` (ACCESS_TOKEN check as today → `ClientSessions` over `LocalBackend` with the lease-based `IpSessionLedger`); its only visible change is `analysisDenied: 'no_token' | 'bad_token'` on the restricted welcome (additive).
   ```ts
   interface AnalysisRouter { route(hello: HelloMessage, peer: { ip: string; connId: number }): Promise<RouteResult>; }
   type RouteResult = { ok: true; route: AnalysisRoute } | { ok: false; reason: AnalysisDeniedReason };
   interface AnalysisRoute {
     readonly limits: Limits; readonly engines: readonly EngineDescriptor[]; readonly node?: WelcomeNode;
     open(deliver: Deliver, peer: SessionPeer): AnalysisChannel;   // called once, after welcome was composed
   }
   ```
3. **`RelaySessions`** (`apps/server/src/hub/RelaySessions.ts`) is a *dumb, validated relay with bookkeeping*: `handle(msg)` sends `client.msg {cid, msg}` over the link (never dropped: these frames are small); `onNodeMessage(msg)` (called by the hub's link for this `cid`) delivers `info`/`bestmove`/`error` verbatim to the player — `Connection.send` applies today's `ServerMessageSchema` check and `info` backpressure. It does not stop, time or order anything: the node's `ClientSessions` is the state machine. Its one guarantee is (b): a `SessionTracker` records every relayed `analyze` as an open search `(sessionId, searchId)` and closes it on its terminal (`bestmove`, or `error` with `searchId`); a session-level `error` (no `searchId`) closes the session; `release` and `close()` close the session but leave its open searches tracked until their terminal arrives (the node still sends `bestmove stopped`). **`onNodeLost()`** then emits exactly one `error engine_crashed {sessionId, searchId}` per still-open search and one `error engine_crashed {sessionId}` per open session without a search, marks the channel dead, and `Connection` closes 1012 (ADR-020 §3). `close()` sends `client.close {cid}` and resolves on `client.closed`, on link loss or after 2 s. `retireAll()` relays a `release` per open session.
   ```ts
   class RelaySessions implements AnalysisChannel {
     constructor(deliver: Deliver, link: LinkPort, cid: string, opts: { logger: PoolLogger });
     onNodeMessage(msg: NodeRelayMessage): void;   // from the hub's node link, already schema-validated (link.ts)
     onClientClosed(): void;                        // node acknowledged client.close
     onNodeLost(): void;                            // link dropped or node.error/link.close
   }
   interface LinkPort { readonly nodeId: string; send(msg: HubToNodeMessage): boolean /* false: link gone */; }
   class SessionTracker {                           // pure, shared by RelaySessions and AccountingChannel
     in(msg: AnalyzeMessage | StopMessage | ReleaseMessage): TrackerEvent[];
     out(msg: InfoMessage | BestMoveMessage | ErrorMessage): TrackerEvent[];
     get openSessions(): readonly string[]; openSearches(sessionId: string): readonly number[];
   }
   type TrackerEvent = { kind: 'session_opened' | 'session_closed'; sessionId: string }
     | { kind: 'search_started' | 'search_ended'; sessionId: string; searchId: number; startedAt: number; endedAt?: number };
   ```
4. **(a) + (d): accounting is a decorator, the same for `local` and remote nodes.** In `ROLE=hub` every channel is wrapped in an `AccountingChannel` (`apps/server/src/hub/AccountingChannel.ts`) that derives session state from the message stream with the same `SessionTracker`: a session *opens* at its first `analyze` — the decorator synchronously reserves one slot per keyed ledger (`ip`: `IpSessionLedger`, `MAX_SESSIONS_PER_IP` across all nodes; `token`: `TokenSessionLedger`, `tier.sessions`) and checks `openSessions < limits.maxSessionsPerConnection`; a failed reservation answers `error no_capacity` (IP) / `limit_exceeded` (token or connection cap) locally and relays nothing. A session *closes* (slots freed) on `release`, on a session-level `error`, on `retireAll`/`close`, and after `sessionIdleMs` without an open search (the hub's idle timer mirrors the node's lease idle release so an idle tab does not pin a slot; the node drops its lease on its own schedule). Consequently the hub's built-in `local` node runs `ClientSessions` with an **unlimited ledger** exactly like a remote node (one accounting implementation on the hub; standalone keeps the lease-based ledger unchanged). **Budget and usage (d) are metered here too:** on `search_ended` the decorator records `min(endedAt − startedAt, maxMovetimeMs + 2 s)` seconds against `(tokenId, nodeId, day)` through a `UsageSink` (HubStore `usage_daily`, batched); for pool routes (`shared: true`) each `analyze` first asks `BudgetSource.remainingSeconds(tokenId)` and answers `error no_capacity "daily pool budget exhausted"` locally when it is ≤ 0 (ADR-020 clarification 7). An infinite search can overrun the budget by at most one `maxMovetimeMs`, which is accepted. Node loss ends every open search at that moment (metered up to it).
   ```ts
   class AccountingChannel implements AnalysisChannel {
     constructor(inner: AnalysisChannel, deliver: Deliver, opts: {
       limits: Limits; sessionIdleMs: number; logger: PoolLogger;
       slots: { ip: SessionLedger; token?: SessionLedger }; keys: { ip: string; tokenId: string; nodeId: string };
       shared: boolean; budget?: BudgetSource; usage: UsageSink;
     });
   }
   interface BudgetSource { remainingSeconds(tokenId: string, now: number): number | null; }  // null = unlimited
   interface UsageSink { record(u: { tokenId: string; nodeId: string; searches: number; engineSeconds: number; at: number }): void; }
   ```
   `AccountingChannel` wraps `deliver` so it sees every terminal message before the player does; `inner` is created with that wrapped `deliver`. Messages the decorator rejects locally never reach `inner`.
5. **(c) Node side.** `NodeLink` (M24-3) keeps one `ClientSessions` per `cid` with `peer = { ip: cid, id: cid }` and a shared `UnlimitedLedger` (`tryReserve` always true): nodes never see addresses, the node-wide cap is the pool's `MAX_SESSIONS` (`no_capacity` from `acquire`), and the per-connection cap is `limits.maxSessionsPerConnection`. The node **clamps** `client.open.limits` with its own: `limits = minLimits(open.limits, own)` (engine-core helper, element-wise minimum; an absent `maxNodes` on one side takes the other's) — defence in depth against a compromised hub (ADR-020 §5). Its `deliver` wraps each message in `client.msg {cid, msg}` and applies the ADR-020 link backpressure rules (drop `info` above 1 MiB buffered or 60/s per search; never terminals). `client.close` → `sessions.close().then(() => send client.closed)`; link loss → close every `ClientSessions`; `node.drain` → stop accepting `client.open`, wait for all channels to close or `drainMs`, then close the link.
6. **Hub node link** (`hub/HubNodeLink.ts`, owned by `LinkServer`): one per connected node; owns `Map<cid, RelaySessions>`, allocates `cid`s (per-link counter, base36), sends `client.open`, dispatches `client.msg` → `relay.onNodeMessage`, `client.closed` → `relay.onClientClosed`, counts unknown-`cid` frames (ADR-020 §3), and on loss calls `onNodeLost()` on every relay. `NodeRegistry` reads `node.status` for the scheduler; the hub does not count a node's sessions itself (a one-RTT race is tolerated: the node answers `no_capacity` if it filled up meanwhile).

**Consequences.**
- One state machine per session (on the node, or in-process for `local`); the hub holds only message-derived bookkeeping, so hub and node cannot disagree about ordering or terminals. `RelaySessions` is testable with a fake `LinkPort`; `SessionTracker` and `AccountingChannel` are pure/unit-testable without sockets or engines.
- Two per-IP accounting rules exist: lease-based in standalone (`ClientSessions` + `IpSessionLedger`, unchanged) and message-based on the hub (`AccountingChannel`); the hub's is slightly stricter until the idle timer fires. Unifying standalone onto the decorator is possible later and is not required.
- `Connection` is touched once more (M24-6): channel creation moves from the constructor to `hello`, `ConnectionOptions.router` replaces four options. Standalone behaviour is unchanged except the additive `analysisDenied` on restricted welcomes; `ws.test.ts` deep-equals of restricted welcomes gain that field.
- `apps/server/src/sessions/AnalysisChannel.ts`, `SessionTracker.ts`, `UnlimitedLedger.ts` (M24-3); `hub/RelaySessions.ts`, `hub/HubNodeLink.ts` (M24-5); `hub/AccountingChannel.ts`, `hub/Router.ts`, `ws/LocalRouter.ts` (M24-6); engine-core `minLimits` (M24-3, unit-tested).

### ADR-020 — spot-check notes (M24-12, 2026-10-25)
Supersedes the numbers sketched in §5 ("0.5 %", "three disagreements within 24 h", "disabled"); implementation in `apps/server/src/hub/SpotCheck.ts`.
- **Sampling:** only finished searches of **shared (pool) routes to remote nodes** (never private routes, never `local` itself), Stockfish family on both sides (Maia/Lc0/Fairy-Stockfish never checked), node depth ≥ 10 with a bestmove and a score. Rate `SPOTCHECK_RATE` **2 %**, at most **1** check at a time and `SPOTCHECK_MAX_PER_HOUR` **20**. A check starts only when `local` runs no player search and still has a free session and engine instance for players; a player search starting meanwhile aborts it (inconclusive).
- **Comparison:** `local` (1 thread, 16 MB) searches to depth **min(node depth, 16)** (`SPOTCHECK_MAX_DEPTH`), capped at 5 s (`SPOTCHECK_MOVETIME_MS`); if its best move differs, a second `go … searchmoves <node move>` evaluates the node's move. Agree when the move is the same or at most **50 cp** worse (`SPOTCHECK_TOLERANCE_CP`), or both evals are decisive in the same direction (±500 cp/mate); the node's reported score must be within **200 cp** of local's eval of its move (`SPOTCHECK_SCORE_TOLERANCE_CP`, 0 = off). Mates map to ±(100000 − n). Illegal moves disagree. Unreached depth, aborts, engine failures and unparsable FENs are inconclusive and not recorded.
- **Reputation:** rolling window of the latest **50** checks of the last 24 h since the end of the last episode (`SPOTCHECK_WINDOW`); with ≥ **10** checks (`SPOTCHECK_MIN_CHECKS`) and a disagreement rate > **20 %** (`SPOTCHECK_MAX_DISAGREE_RATE`) → `suspect` (`suspect_count + 1`, out of the pool at once), cool-down **24 h** (`SPOTCHECK_COOLDOWN_H`), then automatically `normal` with an empty window. The **3rd** episode (`SPOTCHECK_MAX_EPISODES`) is a permanent **pool ban** (schema v2: `nodes.pool_banned_at`, `pool_ban_reason = 'spot-check failures'`, warn log), not `disabled`: the link and the operator's private tokens keep working, the operator's pool switch cannot override it, only the administrator lifts it (`POST /api/portal/admin/nodes/:id/state {poolBanned: false}`, which also resets `suspect_count` and the window; `{poolBanned: true}` bans by hand). `disabled` stays an admin-only action. `NodeView` gains `suspectUntil`, `poolBanned`, `poolBanReason`.
- **Players:** when a node becomes suspect or pool-banned (automatically or by the admin), its existing **shared** relay connections end like a node loss — one `engine_crashed` per open search, then 1012 — and the node gets `client.close`; private connections stay.
- **Privacy / metrics:** `spotchecks` keeps `(node_id, at, agreed)` only (24 h retention); positions live in memory for the duration of one check. `/health/detail.spotchecks` has counters only.
- Rationale for 50 cp (not 30): engine versions, thread counts and the depth cap make 10–40 cp differences between honest results common; the 20 % rate over ≥ 10 checks absorbs residual noise. To be re-measured on the first real community nodes.

## ADR-021 — Move to daisychess.org
**Date:** 2026-10-25 · **Status:** accepted (M27-2; owner decision on the domain, ADR-020 owner answer 3)

**Context.** The app, the operator portal and the hub link ran on `c.referee.at`, a subdomain of an unrelated domain, which ADR-020 left open. The owner registered **daisychess.org**: the community site goes on the apex (M27-1), the app moves. Everything origin-bound moves with it: CSP `connect-src`, the lichess OAuth client ids (lichess shows them on the consent page), `ALLOWED_ORIGINS`/`PUBLIC_ORIGIN` (setup links, portal same-origin check), the nodes' `HUB_URL`, nginx, logs, docs. Browser state is per origin: settings, the server token, the lichess login, the trainer schedule, room seats and the review cache on `c.referee.at` would be invisible on the new name.

**Decision.**
- *Names.* App + portal: `https://play.daisychess.org` (`/`, `/portal/`, `/ws`, `/api/portal/`, `/health`). Node link: `wss://hub.daisychess.org/link` (vhost with only `/link` and `/health`); `/link` on play is an alias with the same limits. One certificate lineage `/etc/letsencrypt/live/daisychess.org/` (apex, www, play, hub).
- *Configuration instead of hard-coding.* `apps/web/csp.config.mjs` exports `APP_HOST` (CSP `wss://play.daisychess.org`), `LEGACY_CSP` and `HUB_CSP`; lichess client ids `play.daisychess.org` (app) and `portal.daisychess.org` (portal), redirect URIs still `location.origin + pathname`; the portal shows `wss://hub.daisychess.org/link` in node snippets when served from play.daisychess.org (`KNOWN_HUB_LINKS`, overridable by `VITE_HUB_URL`, other hosts derive `wss://<host>/link`); the node image defaults an unset `HUB_URL` to the public hub in its entrypoint (not in the image ENV). Server origins stay environment: `PUBLIC_ORIGIN=https://play.daisychess.org`, `ALLOWED_ORIGINS=https://play.daisychess.org,https://c.referee.at` (first entry = setup-link base when `PUBLIC_ORIGIN` is unset).
- *nginx layout.* Shared http-context declarations (all CSP maps, `log_format daisychess`, rate-limit zones) move to `deploy/nginx/daisychess-common.conf` → `conf.d/`: nginx rejects duplicate maps/zones/formats across vhost files and needs a `log_format` before its first use (`sites-enabled/c.referee.at` sorts before `play.*`). Vhosts only reference variables; `scripts/check-csp.mjs` checks the values in the common file and that every vhost `add_header` group sends a CSP through an allowed variable and declares no map. Repo vhost files are complete TLS versions (no certbot `--nginx` editing).
- *Legacy origin and state hand-over.* `c.referee.at` serves a static "moved" page (`apps/web/legacy/`, own strict CSP, `Referrer-Policy: strict-origin`). Its script packs the origin's `daisychess.*` localStorage (except PKCE state) as `{v:1, items, dropped?, hash?}` — raw DEFLATE via `CompressionStream` + base64url (format `1.`), plain JSON when unavailable (`0.`) — into `https://play.daisychess.org/#migrate=<payload>` (`location.replace`). The tokens are the user's own and travel only in the fragment (never sent to a server or logged). Above 16 000 characters it drops the largest non-essential keys, the trainer schedule last, then room seats; settings, lichess login, theme and nick are never dropped; dropped keys are listed in the payload. The app (`apps/web/src/migrate/`, imported in `main.tsx` before the setup link and any store) decodes synchronously with its own capped inflate (512 kB), imports only when `document.referrer` is `https://c.referee.at`, only allow-listed keys with value checks and size caps (≤ 50 room seats), never over an existing key, removes the fragment with `replaceState` (keeping a valid `#/room/…` or `#setup-token=…` from the old URL) and shows "Your settings were moved from c.referee.at" once (naming what was not moved). IndexedDB reviews are not moved (recomputable, ADR-016; token holders get them from the server review store, ADR-017).
- *Transition.* Until a sunset date (placeholder in `deploy/nginx/c.referee.at.conf`, owner to set; proposal six months), c.referee.at keeps proxying `/ws`, `/link`, `/health` and serves the last build's `/assets/` (open tabs), everything else is a 301 to play. Then the proxies go, `ALLOWED_ORIGINS` drops the legacy origin and the name is retired once the certificate lapses.

**Consequences.** No change to the `packages/engine-core` API or the WebSocket protocol. New client ids: lichess tokens issued under `daisychess.c.referee.at` / `daisychess-portal.c.referee.at` keep working (bearer tokens are not origin-bound) and move with the hand-over; the next login shows the new id. Players who open the new address directly (never the old one) or whose browser strips the referrer start fresh (the copy on c.referee.at stays in their browser; opening the old address once still moves it). Setup links already sent point to c.referee.at and keep working during the transition via the follow-up route in the payload; new ones use `PUBLIC_ORIGIN`. Community nodes should switch `HUB_URL` before the sunset. fail2ban jails read all three access logs. The historical text of earlier ADRs keeps `c.referee.at`.

## ADR-022 — iOS and Android apps: Capacitor wrap of `apps/web`
**Date:** 2026-10-26 · **Status:** accepted (M26-0; owner decisions: free, no ads; bundle id `org.daisychess.app` with Associated Domains, registered 2026-10-26)

**Context.** The web app at `https://play.daisychess.org` is a Vite/React SPA with the Stockfish WASM engines in Web Workers (multi-threaded builds need cross-origin isolation, ADR-005/ADR-015), server analysis over WebSocket to the hub (`/ws`, ADR-006/ADR-020), lichess login (PKCE, ADR-012) and a per-device access token delivered by a `#setup-token=` fragment link. The owner wants free, ad-free iOS and Android apps. Constraints: the build host is Debian Linux (no macOS); iOS builds must run on GitHub Actions macOS runners (public repo, free minutes); the Android SDK is installed on the host (build-tools 36, platforms 34–36, NDK 28, JDK 21) but there is no KVM, so no emulator here; the repo is GPL-3.0-or-later and the bundle contains third-party GPL code (chessground, Stockfish). ADR-020 reserved anonymous per-device pool tokens (`POOL_ANONYMOUS`, owner answer 1: later) and a direct-to-node mode for apps.

**Research results that drive the decision** (checked 2026-10-26).
- Android WebView does not support cross-origin isolation at all: Chromium issue 40914606 was closed "working as intended" because WebView runs one renderer process per app, so COOP/COEP headers from `WebViewAssetLoader`/`shouldInterceptRequest` never yield `crossOriginIsolated` or `SharedArrayBuffer`. (A 2026 secondary source mentions a WebView allowlist; unverified, not relied on.)
- iOS: Capacitor issue #6182 (iOS 15.2, Jan 2023) found that COOP/COEP headers returned by a `WKURLSchemeHandler` did not produce isolation even in a bare WKWebView project (headers are lost on the WebView's reload); a loopback HTTP server did work. Capacitor still sets no such headers (discussion #7553 unanswered). Our own memory budget (ADR-015) caps iOS at 2 threads and one instance, so the best case of that plumbing is a 2x gain on iOS only.
- Capacitor 8 is current (minimums: iOS 15.0, Android 7.0/API 24, Node 22, Xcode 26); Capacitor 9 is forecast for late November 2026.
- Google Play: personal developer accounts created after 13 Nov 2023 must run a closed test with at least 12 testers opted in for 14 consecutive days before production access; organisation accounts are exempt.
- Precedent for GPL on the App Store: lichess's own mobile app (GPL-3.0-or-later, bundles native Stockfish, ships chessground's pieces) and the Stockfish team's own iOS app are on the App Store; the FSF's 2010 position (App Store usage rules add restrictions the GPL forbids) led to VLC's removal in 2011 after a *contributor's* complaint, not an Apple policy.

**Decision.**

1. *Wrapper: Capacitor 8, bundled assets, one web codebase.* `apps/mobile` (`@daisychess/mobile`, private) holds `capacitor.config.ts`, the committed native projects `android/` and `ios/App/` (SPM, no CocoaPods/Ruby in CI) and `resources/`. The web app is built once more in a mobile mode (`vite build --mode mobile` → `apps/web/dist-mobile`, `webDir` of Capacitor): same code, three build-time differences — (a) only the `lite-single` engine files are emitted (1.9 MB; `lite` is never usable without isolation and `full` would be a 99 MB runtime download, which Apple guideline 2.5.2 forbids for executable code), (b) the default server URL is the compile-time constant `wss://play.daisychess.org/ws` (`defaultServerUrl()` falls back to `import.meta.env.VITE_DEFAULT_SERVER_URL` when the page origin is not http(s)); the existing `settings.remoteUrl` override stays the self-hosted-hub path, (c) the CSP is injected as a `<meta http-equiv>` generated from `csp.config.mjs` (single source of truth; `connect-src` adds nothing new). A remote-URL shell (loading play.daisychess.org in the WebView) is rejected: Apple 4.2 "minimum functionality" treats it as a web clip, it would not work offline, and the hub's CSP/COOP headers would fight the WebView. Native value beyond the site, all through official `@capacitor/*` plugins: works offline (engine, review, trainer, openings), open-with/import of `.pgn` files from other apps, share sheet for PGN exports and links, haptics, keep-awake during games and drills, safe-area/status-bar theming, universal links for setup and friend-game links, native key-value storage for settings and the token. React Native/Flutter rewrites are rejected (the product is the web app; chessground has no native port).
2. *Engine in the app: single-threaded WASM now, native plugin later, hub for strength.* v1 ships `wasm:lite-single` only; the registry already selects it when `crossOriginIsolated` is false, so no engine code changes. Memory: `lite-single` uses a non-shared, growable 128 MiB memory (no 2 GiB reservation), one instance (ADR-015 budget applies: the WKWebView user agent is an iOS one). The app releases engines on `appStateChange` → background (iOS kills the WebContent process under pressure) and the OOM recovery of M19-1 stays. Threaded WASM is *not* pursued: impossible on Android WebView, needs a loopback HTTP server on iOS for at most 2 threads. The route to multi-threaded full-strength offline analysis is a **native Stockfish Capacitor plugin** (pinned Stockfish source built by NDK/Xcode, UCI over the bridge, `NativeEngineClient` implementing the existing `EngineClient`), scheduled as the last, optional M26 task: same GPL situation as the WASM build, no new licence exposure. Strong analysis in v1 comes from the hub (server engines, Maia), exactly as in the web.
3. *Licensing: ship GPL code, satisfy the GPL ourselves, accept the residual App Store risk.* Facts: the bundle contains our code (GPL-3.0-or-later, we are the copyright holder), chessground (GPL-3.0-or-later, lichess) and the Stockfish WASM build (GPL-3.0-or-later). Apple's App Store usage rules impose restrictions on users that, in the FSF's reading, GPL §10 forbids; Apple itself does not screen for GPL and removes apps only on a copyright holder's complaint. The possible complainants are lichess (ships chessground in its own App Store app) and Stockfish contributors (the team ships its own App Store app and tolerates many GPL Stockfish apps; its enforcement action targeted non-disclosure of source). Risk: low; consequence: removal from the App Store, no damages for a distributor who complies. Mitigation (binding for the tasks): (a) the app's About screen bundles the full GPL-3.0 text and `THIRD_PARTY_NOTICES.md` offline, shows version + git commit and links to the exact `mobile-v*` tag (GPL §6(d) "corresponding source" via the public repository — every store build corresponds to a tag); (b) App Store Connect gets a custom EULA stating that the app is free software under GPL-3.0-or-later and that nothing in the store terms limits the user's rights under that licence (the standard Apple EULA is not used); the Play listing says the same in the description; (c) no native GPL engine in v1 (nothing is newly compiled; the WASM artefacts are those the website already distributes); (d) a GPL complaint is handled by removing the complained-about component, not by arguing. Google Play has no comparable issue; F-Droid (own build, reproducible) is a later option.
4. *Hub URL and token in the app: existing links become universal links; one custom scheme for self-hosted hubs.* The setup link format `https://play.daisychess.org/#setup-token=<token>` and the room links `https://play.daisychess.org/#/room/<id>` are kept; both open the installed app via **universal links / Android App Links** and fall back to the web app otherwise. iOS matches fragments: the AASA claims only `{"/": "/", "#": "setup-token=*"}` and `{"/": "/", "#": "/room/*"}` under `appIDs: ["<TEAM_ID>.org.daisychess.app"]`; Android intent filters cannot see fragments, so the app claims `https://play.daisychess.org/` with `android:path="/"` exactly (autoVerify; `/portal/` and `/assets/` are not claimed). Files live in `apps/web/public/.well-known/apple-app-site-association` and `assetlinks.json` (shipped by `deploy/deploy-web.sh`); nginx `play.daisychess.org.conf` gets `location = /.well-known/apple-app-site-association { default_type application/json; }` (no `add_header`, so it inherits the server headers; HTTPS, no redirect, < 128 kB — Apple's CDN fetches it). The fragment grammar is extended for self-hosted hubs: `#setup-token=<token>&hub=<wss url>` (the token is `dc1_…`/legacy and never contains `&`; `hub` is validated like `settings.remoteUrl`). Custom scheme `daisychess://setup?token=<t>&hub=<wss url>` is the second format, offered by the portal only when `PUBLIC_ORIGIN` is not play.daisychess.org (self-hosters cannot be in our AASA); it carries the known scheme-hijack risk (any app may claim a scheme), the same class as the existing "anyone with this link" warning, and is documented in `docs/SECURITY.md` §2.10. In the app, `appUrlOpen` (plugin `@capacitor/app`) feeds the URL into `consumeSetupLink`/the room router (same parsers, same notices); the lichess login uses the system browser (`@capacitor/browser`) with redirect URI `daisychess://lichess-callback` (PKCE makes an intercepted code useless) and `handleCallback` reads the URL from `appUrlOpen`. The WebView origin is fixed with Capacitor's `server.hostname = 'app.daisychess.org'` (Android `https://app.daisychess.org`, iOS `capacitor://app.daisychess.org`; the name is never served, so no web page can carry that origin); the hub's `ALLOWED_ORIGINS` lists both and `ws/origin.ts` accepts the `capacitor:` scheme in explicit allowlist entries only (the same-host default is unchanged; the WebSocket protocol is unchanged). Pool access for app users remains ADR-020 product question 1 (`POOL_ANONYMOUS`, not part of M26); direct-to-node mode stays deferred (the app keeps a CSP too).
5. *Identity and assets.* Bundle id and `applicationId`: `org.daisychess.app` (explicit App ID, capability Associated Domains only). Display name "DaisyChess"; Android package name identical; custom URL scheme `daisychess`. Icons are rendered from `apps/web/public/brand/daisy.svg` by `apps/web/scripts/render-brand.mjs` (extended): iOS 1024 px on ivory `#f5f5f4` (no alpha), Android adaptive icon (foreground mark, background ivory, monochrome mark), splash = plain background colour with the mark. Store listing text, privacy, support, deletion and accessibility pages are the existing `apps/site` pages (`apps/site/STORE_CHECKLIST.md`); screenshots are rendered with Playwright from the mobile build at the store sizes.
6. *CI and versioning.* `release-mobile.yml` on tags `mobile-v<semver>` (same pattern as `node-v*`): Android job on `ubuntu-24.04` — `bundleRelease` signed with a **new** DaisyChess upload keystore (not the gitref one) and uploaded to the Play **internal** track by the Gradle Play Publisher plugin (service account JSON); iOS job on `macos-15` — `xcodebuild archive` + `-exportArchive` (method `app-store-connect`, manual signing with the owner's existing distribution certificate and a new App Store provisioning profile for `org.daisychess.app`) and `xcrun altool --upload-app` with an App Store Connect API key → TestFlight. No fastlane (no Ruby in the pipeline; two direct tool calls). Marketing version = `apps/mobile/package.json` `version` (checked against the tag); build number (`versionCode`, `CFBundleVersion`) = `github.run_number`, monotonic for both stores. PR CI builds the Android debug APK and an unsigned iOS simulator build only when `apps/mobile/**` or `apps/web/**` change, and runs an emulator/simulator smoke that asserts `isSecureContext === true`, `crossOriginIsolated === false` and a `bestmove` from `wasm:lite-single`. Secrets (names only): `ANDROID_UPLOAD_KEYSTORE_B64`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS`, `ANDROID_UPLOAD_KEY_PASSWORD`, `PLAY_SERVICE_ACCOUNT_JSON`, `IOS_DIST_CERT_P12_B64`, `IOS_DIST_CERT_PASSWORD`, `IOS_PROVISIONING_PROFILE_B64`, `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_API_KEY_P8_B64`; repository variables `APPLE_TEAM_ID`, `PLAY_SIGNING_SHA256` (the Play *app signing* certificate fingerprint for `assetlinks.json`). All actions pinned by SHA as in `ci.yml`.

**Consequences.** No change to `packages/engine-core` or the WebSocket/link protocols. `apps/web` gains a build mode and three small seams (`defaultServerUrl`, CSP meta injection, a `platform` module that is a no-op on the web); `apps/server` gains `capacitor:` allowlist entries; nginx gains one location; the portal gains the app-link variant. The app is a thicker client than the site (offline engine, native integrations), which answers Apple 4.2. Store records, signing material, the API key and the Play closed test can only be done by the owner (checklist in the M26-0 report and `apps/site/STORE_CHECKLIST.md`). Open points for the owner: Google Play account type/age (12-tester rule), Apple Team ID for the AASA, whether the lichess "connect" login needs a Sign in with Apple statement in the review notes (it is not an app account; argued, not implemented).

### Addendum (2026-10-26) — ADR-022 implementation notes (M26-2, M26-3)
- lichess rejects `daisychess://` as an OAuth `redirect_uri` (400, "exotic redirect_uri scheme"); the app's login callback is `org.daisychess.app://lichess-callback` (reverse-domain, RFC 8252 §7.1). `daisychess://setup?token=…&hub=…` stays the setup scheme. iOS registers both schemes; Android has one scheme filter each. The client_id stays `play.daisychess.org` (lichess has no client registration).
- `defaultServerUrl()` uses the built-in hub URL when the origin is not http(s) **or** the app runs natively (Android serves `https://app.daisychess.org`).
- The hub accepts `capacitor://host` origins only when listed explicitly in `ALLOWED_ORIGINS`; production lists `https://app.daisychess.org,capacitor://app.daisychess.org`.
- The mobile build's meta CSP allows `wss:` in `connect-src` so `hub=` links and self-hosted hubs work; the web/nginx policy is unchanged.
- The AASA carries Team ID `PM7LTV7M72`; `assetlinks.json` is rendered at deploy time from `PLAY_SIGNING_SHA256` and never served with a placeholder.
- (M26-8) Play publishing uses `apps/mobile/scripts/play-publish.mjs` against the Android Publisher API v3 instead of the Gradle Play Publisher plugin (no extra Gradle dependency); it runs only when the repo variable `PLAY_PUBLISH_ENABLED` is `true`, i.e. after the owner's manual first upload. The iOS App Store profile is created/reused at build time through the App Store Connect API (`asc-profile.mjs`) with manual signing of the App target; `IOS_PROVISIONING_PROFILE_B64` is an optional fallback. Automatic signing (`-allowProvisioningUpdates`) was rejected: it mints a development certificate per clean runner. `ITSAppUsesNonExemptEncryption=false`. Private keys are only ever stored as GitHub **secrets**, never as variables.
- (M26-4) Native polish, all behind `src/platform/` and lazily imported only in the mobile build: haptics, status-bar style, keep-awake (`@capacitor-community/keep-awake`, MIT, the only maintained option), Preferences mirror (settings, theme and lichess login; localStorage stays the synchronous cache, restored before the first render). Engine release on background reuses the `pagehide`/`pageshow` path (synthetic events after a 2.5 s grace) instead of a new engine API. `viewport-fit=cover` is injected in the mobile build only.
- (M26-5) Files and sharing. iOS: exported type `org.daisychess.pgn` (conforms to `public.plain-text`, extension `pgn`, MIME `application/x-chess-pgn`), `CFBundleDocumentTypes` role Viewer rank Alternate, `LSSupportsOpeningDocumentsInPlace=false`: iOS copies the file into the app's `Inbox`, so no security-scoped access is needed (the web side deletes the copy after reading). Android: VIEW filters for the PGN MIME types and for `content`/`file` URIs whose path ends in `.pgn`; SEND only for the two PGN MIME types, **not** `text/plain` (DaisyChess would show up in every text share sheet; pasted text goes through the Import tab). Capacitor's App plugin only reports VIEW intents, so `MainActivity` rewrites SEND+`EXTRA_STREAM` into VIEW. Files arrive as `file://`/`content://` URLs in the existing `appUrlOpen` dispatcher, are read with `@capacitor/filesystem` as bytes (UTF-8, falling back to Windows-1252; BOM/UTF-16 handled; limit 10 MB; errors as notices) and queued for the Import panel (single game loads, several use the game picker). Sharing: `@capacitor/share` in the apps, `navigator.share` on the web where it exists (the button is hidden otherwise; Copy stays) for the annotated review PGN, the friend room link and the setup link; the file-download export button is hidden in the apps (WebViews do not download blobs).

## ADR-023 — Puzzles: curated lichess puzzles and puzzles from the user's own games
**Date:** 2026-10-26 · **Status:** accepted (M30-0; owner approved both stages 2026-10-26)

**Context.** The owner wants a Puzzles tab: classic tactics puzzles (stage 1) and, later, puzzles made from the mistakes in the user's own reviewed games (stage 2). The lichess puzzle database (<https://database.lichess.org/#puzzles>, CC0) is one `lichess_db_puzzle.csv.zst` of 307 MB (2026-10-02 dump; `sha256sums.txt` on the same site lists its digest) with the columns `PuzzleId, FEN, Moves, Rating, RatingDeviation, Popularity, NbPlays, Themes, GameUrl, OpeningTags, DailyDate`; `Moves` is a UCI line whose first move is the opponent's. A 12 MB ranged sample (238,566 rows; the file is ordered by id, so it is representative) measured: ≈ 6.1 M puzzles in total; ratings spread almost evenly from 600 to 2400; `RatingDeviation` ≤ 80 for 54 %, `Popularity` ≥ 90 for 54 %, `NbPlays` ≥ 300 for 45 %; 73 themes (`short` 50 %, `mate` 32 %, …, `underPromotion` 0.02 %); 20 % of the rows carry opening tags (142 families, 1,235 variation tags); the line length is 2 (15 %), 4 (51 %), 6+ (34 %) plies; one compact row costs ≈ 150 bytes raw and ≈ 55 bytes gzipped; `chess.js` finds every sampled line legal; 5.7 % of the puzzles that end in mate have another mate in one at the last move (lichess accepts those). What exists in the app and must be reused: the openings drill (`apps/web/src/trainer/`, a Zustand store that drives the game store and the board with `movableColor`, suspends the live analysis, respects the human-game lock, takes a search engine through `openSearchEngine` — server when configured, else the pooled browser engine of ADR-015 — and schedules variations with the pure SM-2-light `trainer/schedule.ts` in localStorage `daisychess.trainer`); the review cache (ADR-016, IndexedDB `daisychess-reviews` with an in-memory fallback, `StoredReview {gameKey, startFen, moves, moveDetails[ply] {classification, bestUci, bestLine (UCI ≤ 8), fenBefore, evalBeforeWhite, evalAfterWhite, evalIfBest, playedUci, mover}}`, no headers or names by design); the server review store (ADR-017, `review.get` by game key only — there is no listing); move classification in engine-core (`mistake` = 10–20 win-probability points lost, `blunder` > 20). Constraints: the web is static nginx with a strict CSP (`scripts/check-csp.mjs`; every nginx `add_header` group must repeat the CSP), the apps bundle `apps/web/dist-mobile` (8 MB `check-dist` budget, currently 3.6 MB; must work offline), the mobile WebView origin is `app.daisychess.org`, not `play.daisychess.org` (ADR-022 §4), the host runs Node 24 (`zlib.createZstdDecompress` available), nothing may be tracked, and the board is mouse/touch only (no keyboard move entry exists; only the promotion dialog takes keys).

**Decision.**

1. *Scope and stages.* Stage 1 = Puzzles tab with: solve (opponent's move plays first), move validation with lichess's alternative-mate rule, hints, retry, show solution, analyse afterwards, a local Glicko-2 puzzle rating, theme and opening filters (with a link from the openings trainer), a daily puzzle and a timed rush mode. Stage 2 = puzzles from the user's own mistakes with spaced repetition and a "Your mistakes" list. No accounts, no server state, no metrics: everything the user does stays on the device; the only network traffic is fetching static puzzle files from `play.daisychess.org` (and, as today, engine searches wherever the review engine runs).

2. *Code layout: one new workspace package `packages/puzzles` (`@daisychess/puzzles`), pure TypeScript, no DOM, no Node APIs.* It holds everything the web app **and** the Node build pipeline share, and everything that benefits from headless unit tests: Zod schemas and types of the data formats (`PuzzleRow`, `Shard`, `PuzzleIndex`, `Puzzle`), the CSV row parser and validator (lines → `PuzzleRow`, legality with chess.js), the curation and sharding algorithm (`selectCurated`, `shardByBand`, `buildIndex`, `pickStarter`, `pickDailyPool`), the solver core (`checkMove`, `solutionState` — the puzzle state machine without any store), Glicko-2 (`glicko2Update`), puzzle selection (`choosePuzzle`, `chooseShards` over an index), the daily and rush sequences, theme keys/labels/groups and the opening-tag mapping (`openingTag(name)`), and for stage 2 the pure extraction and line-cutting rules (`mistakeCandidates`, `cutSolution`). `chess.js` (BSD-2) is its only runtime dependency besides `zod`; `engine-core` is deliberately **not** extended (it is the protocol core that also ships in the server and the node CLI, has no chess.js, and gets none of this). The package builds to `dist/` like engine-core (`sideEffects: false`), so `packages/puzzles/scripts/build-puzzles.mjs` (Node, the pipeline CLI) imports the built package; the web imports the source through the workspace alias like it does for engine-core. The web side lives in `apps/web/src/puzzles/` (data access, cache, stores, generator) and `apps/web/src/components/Puzzles/` (UI); `apps/web/src/trainer/schedule.ts` is reused as is for stage 2 (pure functions with a different storage key). The orchestrator adds `packages/puzzles` to the package list in `CLAUDE.md`/the agent definitions.

3. *Data model.* Runtime type (both stages, one solver):
   ```ts
   interface Puzzle {
     id: string;            // lichess PuzzleId, or `m:<sha256 prefix of fen>` for a mistake puzzle
     fen: string;           // position BEFORE moves[0]
     moves: string[];       // UCI; moves[0] is the opponent's move, the user plays moves[1], moves[3], …
     rating?: number; rd?: number;     // lichess puzzle Glicko-2 values; absent for mistake puzzles (unrated)
     themes: string[];      // lichess theme keys (CC0 data); labels are our own words (puzzles/src/themes.ts)
     openings: string[];    // lichess OpeningTags (family tag first), e.g. ['Sicilian_Defense', 'Sicilian_Defense_Open']
     game?: string;         // lichess GameUrl without the `https://lichess.org/` prefix, e.g. '787zsVup/black#48'
     source: 'lichess' | 'mistake';
   }
   ```
   Wire format of a shard (`format: 1`): `{ format, dataset, band, rows: PuzzleRow[] }` with `PuzzleRow = [id, fen, moves /* space-separated UCI */, rating, rd, themeIdx: number[], openingIdx: number[], game]` where `themeIdx`/`openingIdx` index the `themes`/`openings` lists of the index (the shard repeats `dataset` so a cached shard of an older dataset is recognisable). The index (`index.json`, `format: 1`): `{ format, dataset: { source, sha256, lastModified, builtAt, total }, themes: string[], openings: string[], families: number[] /* indexes into openings */, bandSize: 100, shards: { file, band, count, bytes, themes: Record<number, number>, families: Record<number, number> }[], counts: { themes: number[], openings: number[] } }`. Rating bands are 100 points wide (500…2900, the last band open-ended); a shard holds ≤ 2,000 rows of one band, sorted by id; per-shard counts exist for themes and opening **families** only (variation tags are counted globally and filtered client-side inside fetched shards). Every schema is validated with Zod on read (a shard that fails validation is treated as missing, never as data). The starter set (`apps/web/src/puzzles/data/starter.json`, `{ format, dataset, themes, openings, rows, daily: number[] /* row indexes */ }`) is one more output of the same pipeline.

4. *Curation and build pipeline (`packages/puzzles/scripts/build-puzzles.mjs`, run by `deploy/deploy-puzzles.sh` on the owner's host; never in the browser, never in git for the shards).* Input: the zst file, streamed through `zlib.createZstdDecompress()` (Node ≥ 22.15/24; the `zstd` CLI is the fallback when the API is missing) and parsed line by line; pass 1 keeps only rows that pass the hard filter — `Popularity ≥ 90`, `RatingDeviation ≤ 80`, `NbPlays ≥ 300`, `Rating ≥ 500`, legal with chess.js, ≤ 100-char FEN, 2…20 plies (≈ 1.9 M rows, well under 2 GB RSS); pass 2 selects per 100-point band the 16,000 most played rows, then tops up every theme to at least 600 puzzles (most played first) so rare themes (`underPromotion`, `enPassant`, the named mates) stay available; expected ≈ 300 k puzzles (measured on the sample: 268 k at a quota of 14,000). The starter set is 6,000 rows chosen the same way with a quota of 300 per band for 600–2600 plus a theme floor of 20, and carries a daily pool of 1,000 row indexes (rating 1300–2000, `Popularity ≥ 95`, `RD ≤ 75`, shuffled with a seeded PRNG so difficulty varies day to day); it must stay ≤ 1.0 MB raw (asserted by the pipeline and by `apps/mobile/scripts/check-dist.mjs`). Shards are written as `shards/<band>-<16 hex of sha256(content)>.json`, then the index (which names them), so a deployed index never points at a missing shard. Output goes to a temp directory and is rsynced into `/var/www/play.daisychess.org/puzzles/v1/` **without `--delete`**; shards no longer referenced by the index are pruned when older than 30 days (clients with a cached index keep resolving); `deploy/deploy-web.sh` excludes `/puzzles/` from its `--delete` like `/portal/`. The download is cached in `${PUZZLE_CACHE_DIR:-$HOME/.cache/daisychess/puzzles}` and only fetched when missing or when lichess's `sha256sums.txt` lists a different digest (`curl -C -` resumes), verified fail-closed against that digest (and `LICHESS_PUZZLE_SHA256` when set); the dataset digest, `Last-Modified`, build date and row counts are recorded in the index and in `apps/web/src/puzzles/data/SOURCE.md` next to the committed starter (same pattern as the openings table). The script also supports `--sample` (a ranged partial download, for development and the initial starter) and `--dry-run`; its pure parts are unit-tested in `packages/puzzles` against a committed 300-row fixture from the real file. CI never downloads the database.

5. *Delivery, caching, offline, CSP.* Base URL: same origin `/puzzles/v1/` on the web; in the apps (`isNativeApp()` or a non-http(s) origin) the compile-time constant `https://play.daisychess.org/puzzles/v1/` (`VITE_PUZZLES_URL` overrides it for self-hosters, like the default server URL of ADR-022). Fetches are plain CORS-mode `fetch` with no credentials. nginx (`deploy/nginx/play.daisychess.org.conf`): `location /puzzles/v1/shards/` → `try_files $uri =404`, `Cache-Control: public, max-age=31536000, immutable`; `location = /puzzles/v1/index.json` → `Cache-Control: public, max-age=3600`; both repeat the security-header group with `$daisychess_csp` (check-csp rule), set `Cross-Origin-Resource-Policy: cross-origin` (public CC0 data, and the app origin is foreign) and `Access-Control-Allow-Origin $daisychess_app_cors` + `Vary: Origin`, where `$daisychess_app_cors` is a new map in `daisychess-common.conf` that echoes exactly `https://app.daisychess.org` and `capacitor://app.daisychess.org` (empty otherwise). gzip already covers `application/json`. The mobile meta CSP (`mobileMetaCsp`) gains `https://play.daisychess.org` in `connect-src`; the web policy is unchanged (`'self'`). Docker's `nginx.web.conf` gets no location (a 404 makes the client fall back to the starter). Client cache: IndexedDB `daisychess-puzzles` (version 1; in-memory fallback and swallowed storage errors exactly like the review cache) with stores `shards` (key `file`: `{file, dataset, band, rows, bytes, fetchedAt, usedAt}`, at most 64 shards ≈ 10 MB raw, least recently used dropped), `meta` (`index` with `fetchedAt`; refreshed after 24 h, stale copies are used when the refresh fails), `games` and `mistakes` (stage 2, §9). Offline order: cached shards → starter; "Keep puzzles for offline use" in the tab prefetches the first two shards of each band within ±300 of the user's rating (≈ 12 shards, ≈ 3 MB) with a size hint and a progress line. Selection (`choosePuzzle`): window = `[r − 100, r + 200]` for the user's rating `r` (difficulty "easier" `[r − 300, r − 50]`, "harder" `[r + 150, r + 450]`), candidate shards weighted by their matching counts (band, theme, family), at most 3 shard fetches per request, the window widened by ±200 twice before any band is accepted; puzzles already seen (ring of the last 5,000 ids) are skipped; a request that finds nothing shows "No more puzzles for this filter offline" instead of repeating.

6. *Solver semantics (`checkMove`, same for both stages).* The puzzle starts at `fen`; after 600 ms the app plays `moves[0]` (the board is oriented to the user's side = the side to move after it). On each user move: if it equals the expected solution move → correct, the app plays the next opponent move after 300 ms (or the puzzle is solved when the line ends); else if the move **checkmates** → accepted and the puzzle is solved at once (lichess's alternative-mate rule, applies at any step); else → wrong: the move is shown for a moment with a red arrow, then taken back, and "Try again" is offered. Promotions compare the full UCI (`e7e8q`); a promotion to another piece that also mates counts via the mate rule. **Rating is settled at the first terminal event**: the first wrong move, the first hint or "Show solution" settles the puzzle as *failed*; reaching the end without any of them settles it as *solved*; nothing afterwards changes the rating (retries are free). Hint = highlight the piece to move (counts as a miss, like lichess; the UI says so); "Show solution" auto-plays the rest. Puzzles with `moves.length` even (odd number of user moves after the intro) and odd are both valid; the state machine is a pure reducer in the package (`solutionState(puzzle, event) → state`) with the web store only driving the game store, timers and the board (`movableColor` = user colour during the user's turn, `null` otherwise, exactly as `useDrillMovableColor`), suspending the live analysis while a puzzle runs (the `suspendAnalysis/restoreAnalysis` pair of the drill store is extracted to `apps/web/src/engine/analysisPause.ts` and used by both), refusing to start while a human game runs (`humanGameLockReason`), ending when the user loads another position or starts a drill/game, and ended by `stop()` from the drill start. "Analyse": the session ends, the game store keeps the puzzle position with the full solution line as the moves, the live analysis is restored and the Moves tab is shown; "Source game" is an external link to `https://lichess.org/<game>` (`rel="noopener noreferrer"`), absent for mistake puzzles (they link the ledger game instead, §9).

7. *Local puzzle rating: Glicko-2 per device, no account.* `glicko2Update(player, [{rating, rd, score}], tau = 0.75)` implements Glickman's algorithm (system constant 0.75 like lichess puzzles; a fixed rating period per puzzle, i.e. one result per update); the puzzle is the opponent with its stored `rating`/`rd`. Start values 1500 / 350 / 0.09 (converges within ~20 puzzles). Test vector: Glickman's example (1500/200/0.06 against 1400/30 win, 1550/100 loss, 1700/300 loss, τ = 0.5) → 1464.06 / 151.52 / 0.05999. The rating is shown as "1620 ± 85" and is used only to pick the next window (§5). Daily puzzles are rated; rush and mistake puzzles are not. Settings → "Puzzles" offers "Reset puzzle rating and history".

8. *Filters, daily puzzle, rush, trainer link.* Theme filter: one theme (grouped select: Mates, Tactics, Phase, Length, Special) with our own labels. Opening filter: family select and, when the family is chosen and the index counts ≥ 20 puzzles for it, a variation select; counts come from the index (or the starter offline). `openingTag(name)` maps our openings-table names to lichess tags: remove `'`, remove `:` and `,`, spaces → `_`, hyphens kept (`Queen's Pawn Game: Accelerated London System` → `Queens_Pawn_Game_Accelerated_London_System`; family = the part before `:`); the openings panel (browse and drill summary) gets a "Puzzles from this opening" button that opens the Puzzles tab with that family (and the variation when it exists), with a notice when nothing is available offline. Daily puzzle: `starter.daily[(daysSince(2026-01-01 UTC) mod daily.length)]` — the same for everyone on the same app release (the starter is a build artefact; a rebuild changes the pool for the next release, accepted), shown as a card with the UTC date, a streak counter and the last 30 results, stored locally. Rush: 3 or 5 minutes, unrated, a precomputed run of 60 puzzles from the cached shards and the starter with target ratings from 800 rising by 25 per puzzle (clamped to what is available; never a seen puzzle from the last 500), one wrong move = one strike and the next puzzle, three strikes end the run, score = solved; best score per duration kept; no network during a run.

9. *Stage 2 — puzzles from the user's own games.*
   - *Game ledger* (store `games` in `daisychess-puzzles`, ≤ 500 entries, oldest dropped): `{gameKey, startFen, moves (SAN), headers: {White?, Black?, Site?, Date?, Result?, url?}, source: 'play' | 'room' | 'live' | 'pgn' | 'import', userSide?: 'white' | 'black', reviewedAt}`. It is written by a subscriber installed next to `installAutoReview` that watches the review store for a finished or loaded review (`status: done` with a game key) and reads the game store's headers and the active game sources at that moment — **no change to the review code**. The user's side is resolved in this order: engine game → the play store's colour; friend game → `room.state.you`; live game → the lichess `me` side; imports/PGN → a case-insensitive match of `White`/`Black` against the known names (lichess login username, the import tab's saved usernames per site, and a user-maintained "My names" list in Settings → Puzzles); otherwise `undefined`, and "Your mistakes" asks once per game ("Which side were you? ⟨White name⟩ / ⟨Black name⟩ / skip"), storing the answer in the ledger. A ledger game whose local review was evicted is fetched from the server review store with the existing `review.get` (when a server is configured) before generation; nothing is listed from the server.
   - *Extraction (pure, `mistakeCandidates(review, userSide)`)*: every ply where `mover === userSide` and `classification ∈ {mistake, blunder}` and `bestUci` exists, excluding positions where the best move is itself losing (`winProb(evalIfBest, user) < 20`) and duplicates by FEN (`id = m:<16 hex of sha256(fenBefore)>`). The intro move is the opponent's previous move (`moveDetails[ply − 1].playedUci`, with its `fenBefore` as the puzzle `fen`), so a mistake puzzle has exactly the shape of a lichess puzzle; at ply 1 (no previous move) the puzzle starts with the user to move and the intro is skipped.
   - *Validation and line length (`cutSolution`, engine-checked at generation time with the same lease as the drill: `openSearchEngine()` — server when configured, else the pooled browser engine, so it works offline).* Search 1: the mistake position with `multipv: 2`, 1,000 ms (or depth 16 on the server) — the candidate is **skipped unless the best move is clearly better than the second-best**: ≥ 10 win-probability points (the `inaccuracy` threshold) and, for non-mate evals, ≥ 80 cp. The solution is the best line's prefix ending with a user move, at most **3 user moves**: after each user move with a following opponent move in the line, the opponent position is searched with `multipv: 2`, 500 ms; if the best reply is not forced (second-best within 100 cp or within 5 win-probability points) the line is cut *before* that reply (the puzzle ends with the user's move); it also ends at mate or when the line is exhausted. The last position is accepted only if its eval for the user is within 50 cp (or the same mate sign) of the eval after the best move at the start, otherwise the shortest cut that satisfies this is used, else the candidate is skipped. Budget ≤ 4 searches per candidate; generation runs on demand from "Your mistakes" (button "Find puzzles in my games", a queue with progress and cancel), never automatically, so phones do not burn battery after every review.
   - *Storage* (store `mistakes`, ≤ 2,000, due entries never dropped before non-due): `{id, puzzle: Puzzle, gameKey, ply, playedUci, classification, evalBeforeWhite, evalAfterWhite, createdAt, schedule: ScheduleEntry}` with `ScheduleEntry` and `reviewEntry/recordResult/dueKeys` from `trainer/schedule.ts` (success → interval × 2.5 days, failure → due now). "Your mistakes": due count, "Train due" (earliest first), the list grouped by game (names, date, site link when the headers carry a lichess/chess.com URL) with "Open game" (loads the ledger game into the game store and jumps to the ply), delete, and the ask-once prompt for games without a side. Solving uses the same solver and UI as stage 1 with `source: 'mistake'` (unrated; the result records the schedule).

10. *Storage and versioning summary.* localStorage `daisychess.puzzles` (`{v: 1, rating: {r, rd, vol, n}, difficulty, filter: {theme?, opening?}, daily: {streak, last, results: Record<date, 'solved' | 'failed'> (≤ 60)}, rush: {best3, best5}, seen: string[] (≤ 5,000)}`, ≤ 50 kB, parsed defensively like the trainer schedule, not mirrored to native Preferences (the IndexedDB and localStorage of the WebView persist; the mirror stays for settings, theme and the login only) and `daisychess.puzzles.names` (stage 2 names). IndexedDB `daisychess-puzzles` v1 as above; a version bump recreates every store (puzzle data is recomputable or re-fetchable; the ledger and mistakes are then lost — bump only with a migration in `onupgradeneeded`). Data formats carry `format: 1` in the URL path (`/puzzles/v1/`) and in every file; a format change is a new path and a new `PuzzleIndexSchema`, so old builds keep reading the old files until the prune. The lichess puzzle id is the stable identity across datasets (seen-list, daily history).

11. *Accessibility, privacy, attribution.* The puzzle panel takes moves also as typed SAN (an input "Move, e.g. Nf3", resolved with `resolveSan` from `trainer/drill.ts`), which makes puzzles solvable without a pointer; the status line is an `aria-live="polite"` region; the hint/solution/retry controls are plain buttons. Privacy: no identifiers leave the device; shard requests are ordinary static requests (the path names a rating band; access logs keep the stock 14 days) — one sentence in `docs/PRIVACY.md`; stage 2 reads the local review cache and the server store by game key only. Attribution: `THIRD_PARTY_NOTICES.md` ("Distributed with the web app": the lichess puzzle database, CC0-1.0, dataset digest/date in `SOURCE.md`; the test fixture is part of it), the About → Licences attributions ("Puzzles: lichess.org puzzle database, CC0"), and a line in the Puzzles tab footer "Puzzles from the lichess.org database (CC0)". Theme descriptions are written by us (the lila translation files are AGPL and are not copied). Store listing: the "puzzle"/"puzzles" keyword returns and a PUZZLES paragraph is added (M30-13).

**Consequences.** New package `@daisychess/puzzles` (+ chess.js there), no change to `packages/engine-core` or to the WebSocket protocol; the hub/server is untouched (static files only). The web bundle gains one lazy chunk of ≈ 1 MB (starter) plus the puzzle UI; `dist-mobile` stays under the 8 MB budget (≈ 4.8 MB expected; `check-dist` asserts the starter size). nginx gains two locations and one map (installed by the orchestrator; `check-csp.mjs` covers them); `deploy-web.sh` must exclude `/puzzles/` or the next web deploy deletes the shards. `/var/www/play.daisychess.org/puzzles/v1/` holds ≈ 45 MB raw (≈ 17 MB over the wire gzipped, fetched piecemeal); a monthly `deploy-puzzles.sh` run downloads 307 MB once per new dump and takes a few minutes. A rebuild changes the committed starter (≈ 1 MB diff) — regenerate it only when the dump changes. The daily puzzle is deterministic per app release, not across releases. Hints and solutions count as failures (lichess convention). Stage 2 depends on reviews having been run (Fast suffices: the start search re-checks the position) and on knowing the user's side; PGNs of other people's games produce no puzzles unless a side is picked. Theme labels and descriptions are our own text and may be rephrased freely.

**Open questions for the owner (product level).**
1. Hint cost: a hint counts as a miss (lichess behaviour, decided here). Alternative: the first hint (piece only) is free and only "Show solution" counts. Keep the lichess rule?
2. Daily puzzle identity: "same for everyone on the same app release" (bundled pool) is proposed; the alternative is to fetch the daily pool from the server (same for everyone online, no daily puzzle offline on the first day). Fine with the bundled pool?
3. Rush format: 3 and 5 minutes with three strikes, unrated (decided). Should rush results also show a "best streak" on the daisychess.org site? (No — nothing leaves the device; mentioned only because it is the one place where sharing a score is common.)
4. Stage 2 trigger: puzzles are generated on demand from "Your mistakes" (battery/engine cost), not after every review. Acceptable, or should it run automatically on server reviews only?
5. Pipeline cadence: run `deploy-puzzles.sh` by hand after each monthly lichess dump (recommended; the starter commit is a manual step), or a monthly systemd timer on the host (owner-only step)?

### Addendum (2026-10-26) — ADR-023 owner answers
Hints count as a miss for the rating (lichess rule); the daily puzzle comes from the bundled pool (offline, same per release); stage-2 puzzles are generated on demand from "Your mistakes"; rush 3/5 min, three strikes, unrated, scores on the device only; the puzzle pipeline runs manually after each monthly lichess dump.
